# 蓝鲸记忆中枢 · BlueWhale Memory Hub

> 跨渠道 AI 记忆服务：让 MC 插件里的角色、QQ 群机器人、直播弹幕机器人
> 共用同一份记忆，彼此记得对方渠道发生过的事。
>
> **状态：可运行（v0.1.0）。341 项测试全绿。已产出 macOS DMG。**

---

## 快速开始

```bash
# 构建
cargo build --release

# 启动（默认只听本机，因为没有 token）
BLUEWHALE_DATA_DIR=$HOME/.bluewhale-memory ./target/release/bluewhale-memory serve

# 要让内网访问，必须带 token 和后台口令
BLUEWHALE_TOKEN=<至少16字符> \
BLUEWHALE_PANEL_USER=admin \
BLUEWHALE_PANEL_PASSWORD=<至少8字符> \
BLUEWHALE_BIND=lan ./target/release/bluewhale-memory serve

# 浏览器打开 http://<本机IP>:25590 → 登录页 → 管理后台
```

打包：

```bash
./packaging/make-dmg.sh     # 产出 dist/bluewhale-memory-<ver>-macos-<arch>.dmg
./scripts-verify.sh         # 开发/打包前必跑：格式+clippy+单测+集成+release
```

## 五条铁律

1. **备份只能走 `VACUUM INTO`（内置 `snapshot` 命令）。**
   直接 `cp`/`rsync`/`tar` 抓 `.db` 会静默丢 WAL 里已提交的数据
   （实测丢 5/408 条，零报错）。
2. **不跨机器共享 `.db` 文件。** WAL 依赖共享内存，网络文件系统上会损坏。
   多机共享只能走本服务的 HTTP 接口。
3. **没有 token 就强制只听回环。** 不存在「开着但不要密码」这个状态。
4. **身份绑定必须人工确认。** 猜错会把两个人的记忆混成一个人，且不可逆。
5. **时间轴以 `at_ms`（现实 UTC 毫秒）为唯一主轴。** 游戏日 `g<N>` 只是 MC 渠道的标签。

### 认证

两条鉴权链**互不替代**：

| 入口 | 凭据 | 给谁 |
| --- | --- | --- |
| `/` 及 `/api/admin/*` | **会话 cookie**（`HttpOnly` + `SameSite=Strict`） | 人在浏览器里 |
| `/v1/*` | **`X-API-Token`** header | 脚本、其他服务 |

cookie 不能调 API，token 也不该塞进浏览器。**一个泄了不会带出另一个。**

安全默认：
- 未配置 `PANEL_PASSWORD` 且监听内网 → **后台一律 401**（不给「打开就能看」留缝）
- 口令错固定延时 400 ms，让脚本化猜测没意义
- 会话 **1 年**有效，落盘到 `panel_session` 表——进程重启不掉线（操作者要求「长期有效」）
- 登出会立刻从表里删掉那条会话
- 会话 id 来自 `/dev/urandom`，定长比较防时序侧信道

## 已实现的能力

### 记忆与权重

- 24 张表（`schema 11`）：
  - 身份：`person` / `person_account` / `person_scene`
  - 记忆：`event` / `fact` / `journal` / `diary`
  - 人格：`self_narrative` / `mood` / `trait` / `relation` / `promise`
  - 渠道：`channel_message`
  - 规划：`plan` / `plan_item`
  - 知识库：`kb` / `kb_doc` / `kb_chunk`
  - 检索与运维：`recall_log` / `injection_replay` / `snapshot` / `rollback_log` / `panel_session`
- **可配置权重模型**（`WeightConfig`，全部可调）：
  `weight = importance^exp × 衰减(半衰期) × 强化(回忆次数,有上限) × 渠道可信度`
  - 半衰期默认 30 天，衰减有下限（老记忆不归零，仍可显式检索到）
  - 人写的（`tier=curated`）不衰减
  - 强化有上限（默认 ×2），防止它反复念同一件事
  - 渠道可信度：MC 1.0 / QQ 0.9 / 直播 0.8（弹幕可能有玩笑和反串）

### 身份与称呼

- **单主体**：全库只有一个对象；`person` 是「它认识的人」，不是记忆的归属者。
- **跨渠道身份**：MC UUID / QQ 号 / 直播 uid 绑到同一个 `person`，记忆自动合并。
- **各场景里的称呼**（`person_scene`）：同一个人在 MC / QQ 私聊 / QQ 群 / 直播间被叫的名字不一样。
  人工填了以人工为准，留空按渠道账号与群名片自动推导；面板「身份」页维护、关系页只读。
- **称呼归一**（`POST /v1/name/normalize`）：调用方在发送回复前过一下，
  把回复里的场景称呼换成身份显示名（例：QQ 群名片「啥子猫」→ 显示名「姆姆」）。
  2 字以下不换、有歧义不换、长名字优先。

### 检索（中文 BM25）

旧版是 `summary.contains(q)` 的**纯子串匹配**。它有两个不会报错的症状：

| 症状 | 实测 |
| --- | --- |
| 换个说法就查不到 | 8 个自然改写提问，字面命中 **0/8** |
| 换十个问题，注入的记忆段一模一样 | 唯一性 **1/10** |

第二个症状的根因不只是子串匹配：未命中时靠 `weight` 兜底，而 `weight`
只由重要性/时效/渠道决定、**与提问无关**；更糟的是这些兜底行也被
`note_recalled` 计入 `recall_count`，于是越兜底越重、永远下不来（自我强化环路）。

现在是 `src/rank.rs` 的中文 BM25：

- **字级 2-gram**，不需要词典、不处理未登录词；同时产单字，但单字权重 ×0.35
- **停用字软降权 ×0.15**，不是删除 —— 硬删会连带丢掉「挖到」这种含实义词边界的 bigram
- **泛化词表**（「东西」「什么」…）单独处理：它们统计上并不高频
  （实测「东西」df 占比 3.2%，比「钓鱼」的 8.9% 还稀有），阈值拦不住
- **实义命中**才判 `hit`：多字、非停用字、非泛化词。纯虚词提问（「在吗」）仍返回兜底行，
  但一条都不标命中
- **兜底行不计入 `recall_count`**，切断上面那条自我强化环路

修复后：改写提问 **7/8 命中**，不同提问唯一性 **10/10**，p50 **0.74 ms**（752 条 / 2.6 万字符）。

**`journal` 同时并入了检索面**：它占全库可检索文本的 **58.6%**（585 条），
旧实现只查 `event` + `fact`，等于一多半记忆永远想不起来。

> 仍然**不是语义检索**：同义词、跨语言查不到。那要向量模型，
> 是另一次改动 —— 当前取舍仍是「一个二进制 + 一个 .db」。

### 知识库（外部资料，与记忆分开）

记忆和知识库是**两套东西**，不是一张表多一个字段：

| 维度 | 记忆 | 知识库 |
| --- | --- | --- |
| 时效 | 半衰期 30 天衰减 | **不衰减** |
| 失效 | `expires_ms` / `superseded_by` / 回滚 | 只有版本覆盖 |
| 权重 | importance × 衰减 × 强化 | importance 概念不成立 |

混进 `fact` 表会让资料被衰减悄悄淡掉、被回滚一起抹掉 —— 都不是用户的意思。

**接口**（`X-API-Token` 鉴权）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/v1/kb` | 建库（同 id 幂等） |
| GET | `/v1/kb/list` | 库与文档列表 |
| POST | `/v1/kb/doc` | 导入文档（按内容指纹幂等） |
| POST | `/v1/kb/search` | 检索 |
| GET | `/v1/kb/health` | 嵌入状态与积压 |

**已接入 `/v1/context`**：命中时自动注入一段 `# 你查到的资料（不是你的亲身经历）`，
位置在「记得的事」之后、「最近发生的事」之前。**没有命中就不出现**，不占预算。

有注入门槛（`vec ≥ 0.42 或 lit ≥ 0.30`，可配）：实测无关提问也能拿到
`vec ≈ 0.29~0.36`，不设门槛的话每轮闲聊都会塞进不相关的内容。

**面板**：侧栏「知识库」页可以新建库、导入文档、删除文档、检索测试、重建向量。
检索测试会给每条结果标出它是靠**向量**还是靠**字面**命中的（`lit=0` 意味着
字面完全没重叠，纯靠语义）。

**默认关闭**（`BLUEWHALE_KB_ENABLE=true` 才启用）。不启用时与加这个功能之前完全一致。

**检索是 RRF 融合**（向量排名 ×2 + 字面排名 ×1，k=60），**不是加权和** ——
实测加权和是四种融合里最差的（MRR 0.441 vs 0.500），因为 BM25 分数与 cosine
不在同一尺度，归一化会让相对权重随查询漂移。

**分块按语义边界**（标题 → 段落 → 句子），不做重叠窗口。
实测「整篇够短就不切」是错的：一份 200 字文档写了三节，整篇塞成一块后
问其中一节的内容拿到的是混合向量。**有标题就按标题切，哪怕整篇很短。**

**嵌入服务是软依赖**：挂了自动退回纯字面，接口仍返回 200，并在响应里
带 `degraded` 字段。真机验证（`qwen3-embedding:0.6b-q8` / 512 维）：
7 条查问全部命中正确小节，其中 **4 条字面完全无重叠**（`lit=0.000`），纯靠向量。

### 回滚（逻辑删除、可撤销）

```bash
bluewhale-memory rollback --to <毫秒时间戳>   # 忘掉该时刻之后的记忆
bluewhale-memory undo --id <n>                # 撤销
bluewhale-memory rollback-history             # 看历史
```

- 回滚是**标记删除**（`deleted_by`）+ 读路径一律 `WHERE deleted_by IS NULL`
- **多次回滚可逐层撤销**，乱序撤销也能工作
- `purge` 才物理清理，且不可逆
- 边界是**严格大于**：恰好等于目标时刻的记录保留（快照里就有它）
- 身份绑定**不参与回滚**——忘掉记忆不等于忘掉「这个人是谁」

### 每日快照

- 每小时检查一次，`ensure_daily` 保证同一天只有一份
- 每次生成后立刻 `PRAGMA quick_check` + 记录 `sha256`
- 篡改/丢失能被 `verify` 检出
- 保留 30 天（可配），但**永远至少留最新一份**

用量/对话记录是 MC 的诊断数据；进行中/总规划/角色控制是 MC 的运行时状态。
要让 Hub 显示它们，得让 MC 定时推送——那是一个新的数据通道，
不是「把页面搬过来」。需要就说一声。

## 从旧库迁移存量数据

Hub 建起来是空库，MC 侧已有的记忆要迁过来：

```bash
  --from ~/MC_AI/shared/deepseek_mc/memory.db --dry-run

# 确认无误再真迁（会自动先拍一张快照）
./target/release/bluewhale-memory migrate \
  --from ~/MC_AI/shared/deepseek_mc/memory.db
```

**规划要单独迁**（它不在 SQLite 里，是 `plans/<角色名>/g<N>.json` 文件）：

```bash
./target/release/bluewhale-memory migrate \
  --from ~/MC_AI/shared/deepseek_mc/memory.db \
  --plans ~/MC_AI/shared/deepseek_mc/plans
```

**三条保证**：
- **只读源库**：迁移工具用 `SQLITE_OPEN_READ_ONLY` 打开，改不动旧库
- **幂等**：反复跑不会产生重复行（靠源 id / `dedup_key`）
- **字段翻译**：`event.type → kind`、`subject_id → person_id`、
  `persona_trait → trait`、`qq_message → channel_message`
- 时间戳**原样保留**，否则时效衰减全乱

## 关键设计取舍（都有实测依据）

**读连接池**：每次读都 `Connection::open` 看似无害，实测 32 并发下 p99 从 9ms 飙到 246ms
（打开文件 + 解析 WAL 索引约 100–200 µs）。池化后读吞吐 **2,255 → 8,325 req/s**。

**写串行**：SQLite 只有一个写者。给连接池只会把并行转换成 `SQLITE_BUSY`。
写走单连接 + 短事务，比「并发写 + 重试」快得多。

**`rusqlite` 必须 `spawn_blocking`**：它是同步的，直接在 async 任务里调用会卡住整个 executor。

**WAL 文件大小 ≠ 未合并数据量**：SQLite 的 checkpoint 是**覆盖**而非截断。
实测 WAL 稳定 4.1 MB 时 `wal_checkpoint` 返回 `log_pages=0`——数据其实早已合并。
拿文件大小当 checkpoint 健康指标会误报。
