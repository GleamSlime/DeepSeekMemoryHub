# 契约：`GET /v1/context`（中枢 → QQ 机器人）

> 这份契约是**两个 agent 并行开发的唯一接口约定**。任何一方想改字段，先改这份文件。

## 为什么需要它（不是"再加个接口"）

现有链路实测是**静默失效**的：

1. 插件回答前调 `GET /v1/recall?q=<群友那句话>`。
2. 中枢的 `recall` 对非空 `q` 曾是**纯子串匹配**（`summary.to_lowercase().contains(&needle)`）。
3. 于是「在吗」「你最近干嘛」「最近」「心情」全部返回 `[]`（已实测）。
4. 插件拿到空数组 → 不注入 → 模型照常编。**没有任何报错**。

而且 `recall` 曾经只查 `event` + `fact` 两表，看不到 `journal` / `diary` / `plan_item`。
用户要的「知道最近在服务器中干什么」恰好全在它看不到的那三张表里。

> **以上四条已修复（2026-10-30）**：检索换成中文 BM25（`src/rank.rs`），
> `journal` 已并入检索面。修复后的实测：8 个自然改写提问 **7/8 命中**，
> 十个不同提问注入的记忆段**唯一性 10/10**（修复前 1/10）。

所以正确做法不是让插件拼 6 次请求（`recall` + `journal/list` + `diary/list` + `plan` + `mood` + `self`，
每个都要在**回答之前**跑完，延迟叠加），而是中枢提供**一次调用、返回一段可直接塞进 prompt 的文本**。

---

## 请求

```
GET /v1/context?budget=1200&q=<群友那句话>&topk=5
Header: X-API-Token: <token>
```

| 参数 | 类型 | 缺省 | 说明 |
| --- | --- | --- | --- |
| `budget` | usize | `1200` | 返回文本的字符上限，**clamp 到 `[200, 4000]`** |
| `q` | String | `""` | 群友这句话，用于挑相关记忆。空 = 只按时间/权重取 |
| `topk` | usize | `5` | 记忆条目上限，clamp `[1, 30]` |

## 响应 200

```json
{
  "text": "# 你最近在做什么\n- 今天在盖房子…\n\n# 你记得的事\n- …",
  "chars": 218,
  "parts": ["server", "plan", "memory", "names", "events", "group", "diary"],
  "dropped": ["diary: 超预算"],
  "generated_ms": 1793240000000
}
```

| 字段 | 说明 |
| --- | --- |
| `text` | **可直接拼接进 system_prompt 的 markdown**。没有任何可注入内容时是空串 `""`（不是 null） |
| `chars` | `text` 的字符数（Rust `chars().count()`，不是字节数）—— 调用方用它记账 |
| `parts` | 实际进了 `text` 的段落名，排查「为什么它不提这件事」时看这个 |
| `dropped` | 被预算挤掉的段落及原因，**必须写具体原因**（`"diary: 超预算"` 而不是 `"diary"`） |
| `generated_ms` | 生成时刻 |

**错误**：只有 `401`（token 错）和 `400`（参数非法）。**任何一张表读失败都不许整体 500** —— 少一段继续返回，
把原因写进 `dropped`。

---

## `text` 的段落顺序与格式

顺序是**刻意的**：越靠上越稳定、越不可替代。预算不够时从下往上丢。

### 1. `# 你最近在做什么`（来自 `plan` / `plan_item`）

取 `deleted_by IS NULL` 的**最新一张** plan，列出 `summary` 和最多 6 个 item。

```
# 你最近在做什么
- 今天的打算：矿也挖了、煤也攒了，今天该把家往上盖一盖。
- 已完成：把背包里的铁矿烧成铁锭
- 已完成：给小屋再垒一段墙
- 还没做：清包：圆石和零碎归箱
```

- item 的 `state` → 中文：`done`→`已完成`、`todo`→`还没做`、`deferred`→`先搁着`、`abandoned`→`不做了`
- `done` 的最多列 3 条，其余最多列 3 条 —— 全列出来会把预算吃光
- plan 表为空 / 全是 `deleted_by` → **整段省略**（不要写「暂无计划」，那是噪声）

### 2. `# 你记得的事`（来自 `recall` 的检索结果）

调内部检索（`q` 参与），最多 `topk` 条。**这一段的检索必须修**——见下面「同时要修的 recall」。

```
# 你记得的事
- 在 y=-54 发现了钻石矿脉
- 主人爱吃的: 鱼
```

### 2.5 `# 称呼对照`（只在**这一轮提到的**人身上出现）

同一个人在不同渠道叫法不同：身份显示名「姆姆」、QQ 群名片「啥子猫」、MC 名「GleamSlime」。
模型在群里看到的是群名片，不知道那就是姆姆。

**触发条件写死为「这句话里出现了他的名字」**（显示名或任一场景称呼，≥2 字、无歧义）。
没提到就不出现——把整张身份表塞进上下文既费 token，也会让模型把不相干的人扯进来。

```
# 称呼对照
同一个人在不同地方叫法不同，别当成两个人：
- 姆姆：QQ 群叫「啥子猫」、MC 里叫「GleamSlime」
```

- 出现在 `text` 里时，`parts` 会多一个 `"names"`；
- 同一称呼指向两个人时**不触发**（与 `/v1/name/normalize` 同一套歧义规则）；
- 所有场景都等于显示名的人不占一行；
- 最多 3 个人，全部返回不超过一百多字。

> 回复方向的反向改写不在这个接口里：调用方发送前调 `POST /v1/name/normalize`
> 把回复里的场景称呼换成显示名（见《对接指南》5.4）。

### 3. `# 最近发生的事`（来自 `event`，`channel='mc'`）

最近 **6** 条，`at_ms` 倒序，每条一行，**带相对时间**（「今天」「昨天」「3 天前」）：

```
# 最近发生的事
- 今天 · 被苦力怕炸了
- 昨天 · 把矿洞入口挖通了
- 3 天前 · 发现了钻石矿脉
```

### 4. `# 群里最近说的话`（来自 `channel_message`，`channel='qq'`）

最近 **8** 条，`at_ms` 正序（**先说的在前**，读起来像对话）。**发送者名字要打码口径由调用方决定**——
中枢原样给 `sender_name`，但如果 `sender_name` 为空则用 `account` 的末四位（`***0001`），
**绝不输出完整 QQ 号**。

**发送者会换成身份显示名**（2026-10-31）：QQ 号绑过身份的人，这里显示「姆姆」而不是群名片；
没绑过的人、以及名字对不上的人保持原样。映射顺序是**先按 QQ 号、再按名字**（名字有歧义不换）——
群名片会改（「啥子猫」→「啥子喵」），账号不会。

消息**内容里的 @昵称**也一起换（存在库里的是纯文本 `@啥子喵(478889187)`）：
`@什么名字` 里的名字会变成显示名，QQ 号那串括号保持原样。

```
# 群里最近说的话
- 姆姆：明天我去看你钓鱼啊
- ***0001：你昨天挖到什么了
```

### 5. `# 你上次记的日记`（来自 `diary`，`kind='day'`）

最新一篇的 `title` + `body` 前 **80** 字。

```
# 你上次记的日记
《水边那两竿》今天本来打算先把箱子归了，再去水边守着…
```

### 6. `# 你现在是什么心情`（来自 `mood`）

**只在这一段有内容时输出**：`label` 不是「平静」时才写。平静是默认值，写出来只是噪声。

```
# 你现在是什么心情
有点烦，刚被炸过。
```

（`mood` 有 `reason` 字段，实测值是「有人说话」这种。**只在 reason 非空且非默认值时用它**，
否则只写 label。）

## 同时要修的 `recall`（不是可选项）

`GET /v1/recall` 曾经的行为是「非空 q 不命中就丢」，导致自然语言查询稳定返回空。
改成 **关键词命中优先，未命中兜底**：

- 保留 `why` 的既有取值：`"关键词命中"` / `"权重最高"`（前端和文档已经在用这个词）
- 排序键 **`(是否命中, score, weight, at_ms)`** 字典序 —— 命中的一定排在未命中的前面，
  不能让一条高权重但不相关的老记忆挤掉真正相关的那条。
  `score`（相关度）排在 `weight`（重要性/时效）之前，因为 `weight` 与提问无关
- 这样 `q` 非空时**永远不会返回空数组**（除非整个库确实是空的）

> **后续（2026-10-30）**：「命中」的判定已从 `contains(q)` 换成 BM25 相关度，
> 并新增 `score` / `matched` 两个字段。`why` 的取值**没有变**（仍只有那两个）。
> 详见 `docs/对接指南.md` §4.1。

这条改完，`/v1/context` 的第 2 段才有东西可用。

## 同时要补的两个接口

### `GET /v1/plan/list?limit=10` / `GET /v1/plan/{id}`

规划数据现在**没有任何 `/v1` 出口**（只能 cookie 登后台，API token 拿不到）。
外部程序（QQ 机器人、别的东西）要读「今天计划完成到哪」必须有这个口。

```
GET /v1/plan/list?limit=5
→ [{"id":"plan-xxx","planning_day_id":"g1","summary":"…","game_day":1,
    "created_ms":…,"updated_ms":…,
    "total":5,"done":3,"deferred":1,"todo":1,
    "items":[{"id":"i1","title":"…","state":"done","reason":null,"outcome":null}]}]
```

`items` 要带上（调用方可能只想看概要，但带上的成本很低）。

### `DELETE /v1/message/{id}`

`channel_message` 是三张可编辑表里**唯一没有删除口**的。清理误入库的群消息、删错同步都靠它。
走和 event/fact/journal 一样的 `mark_deleted`（逻辑删除 + `rollback_log`）。

---

## 另外两条防御（顺手，但很重要）

1. **`dedup_key: ""` 必须归一成 `null`**。实测：第一条 `dedup_key:""` 写入成功后，
   **之后所有** `dedup_key:""` 的事件都被吞（`duplicate:true`），无论 summary 完全不同。
   这是个永久性的静默数据丢失。在 `/v1/event`、`/v1/journal` 的入口把空串过滤掉。
2. **`/v1/message` 的 `message_id: ""` 同样归一成 `null`**（实测第一条就被吞）。

---

## 不做的事（明确划界）

- **不把 MC 实时状态搬进中枢**。中枢有 `plan`，但它的数据要靠 MC 推；本轮不改 MC→中枢 的 plan 推送。
  「此刻在干什么」由插件**直接问 MC** 的 `/qq/doing`（已有的口），中枢只管长期记忆。
  两个源各管一段，谁也不冒充谁。
- **不做向量检索**。当前规模（409 手帐 / 135 事件）下子串 + 权重就是毫秒级。
- **不改 `text` 之外的既有接口语义**。

# 追加（2026-10-29 晚）：`scene` 场景隔离 —— 私聊接入

> 用户要求「QQ 群对话合理入库」扩展到**私聊**，并明确选 A 方案：
> 私聊单独存，只对私聊场景可见，群场景看不到私聊内容。

## 请求加一个参数

```
GET /v1/context?budget=1200&q=…&topk=5&scene=group|private
```

| `scene` | 「最近说的话」段取什么 |
| --- | --- |
| `group`（**默认**） | `group_id IS NOT NULL AND <> ''` |
| `private` | `group_id IS NULL OR = ''` |

**默认必须是 `group`。** 「忘了传参数」是最常见的调用方式，默认必须落在**给出更少**的那一侧。
无法识别的值（含空串、`GROUP`、拼错的词）**一律回落到 `group`**，不能因为写错参数而放宽。

## 响应加一个字段

```json
{ "text": "…", "chars": 218, "parts": [...], "dropped": [...],
  "generated_ms": …, "scene": "group" }
```

`scene` 回显**服务端实际采用**的场景。用途：排查「我传了 private 怎么还是群聊」——
传了无法识别的值时这里会显示 `group`，而不是静默按调用方以为的那个走。

## 段落标题随场景变

| 场景 | 标题 |
| --- | --- |
| `group` | `# 群里最近说的话` |
| `private` | `# 你和他最近聊的` |

两个场景用不同标题，模型才分得清自己在跟谁说话。

## 数据约定（写入口必须守）

| 来源 | `channel` | `group_id` |
| --- | --- | --- |
| 群聊 | `qq` | 群号（非空） |
| 私聊 | `qq` | **不传这个键**（不是传空串） |

`group_id` 传空串在 SQL 里仍是**非 NULL 值**，`IS NULL` 那半个条件抓不到它，
两条分支的判定必须同时写 `= ''`，否则那条消息两个场景都看不到（静默丢失）。

## 必须有且必须会失败的判据

> 同一条私聊消息，`scene=private` 看得到，`scene=group` **看不到**。

这是 A 方案的全部价值。它不能只是「打印出来看看」——谁哪天把 `group_id IS NULL`
那半个条件改没了、或者把默认从 `group` 改成 `private`，群里就能问出别人的私聊，
而**功能看起来完全正常**。只有这种断言能在 CI 里拦住它。

已落地的判据（`MemoryHub/tests/http_api.rs`，6 条）：
`scene_私聊消息在群场景里一个字都不出现` / `scene_私聊场景只给私聊且标题不同` /
`scene_不传参数时等同于_group_也就是更严的那一侧` /
`scene_无法识别的取值回落到_group_而不是_private` /
`scene_group_id_是空串时算私聊不算群聊`，外加插件侧 `selftest.py` 的 12 条。
