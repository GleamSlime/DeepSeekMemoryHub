# 蓝鲸记忆中枢 — 对接指南

> 给**其他项目**用。你要让自己的程序（Minecraft 插件、QQ 机器人、直播弹幕机器人、
> 任何别的东西）往这里写记忆、或从这里取记忆，看这一份就够。
>
> 全部示例都是**真实请求与真实响应**，不是设计稿。

---
> **单主体设计（schema v7 起）**：中枢是**一个人的**记忆，不是多人的。
> 所有接口里原来的 `companion_id` 字段/参数**已删除**——旧客户端继续传不会报错
> （JSON 多余字段被忽略、query 参数被忽略），但它的值**不再有任何作用**。
> 表上统一为 `owner_id`，固定值 `me`，不参与筛选。



## 0. 三十秒上手

```bash
# 1. 探活（不需要 token）
curl http://<主机>:25590/v1/health

# 2. 写一条记忆
curl -X POST http://<主机>:25590/v1/event \
  -H "X-API-Token: <你的token>" \
  -H "Content-Type: application/json" \
  -d '{"channel":"mc","kind":"task.done",
       "summary":"盖好了小屋的东墙","importance":0.85,
       "dedup_key":"mc-2026-10-27-wall-east"}'

# 3. 取记忆（给提示词用）
curl -H "X-API-Token: <你的token>" \
  "http://<主机>:25590/v1/recall?topk=5"
```

三条就够跑通。下面是把三条做对的细节。

---

## 1. 三条必须理解的概念

### 1.1 单主体 —— 谁在记

这个中枢只服务**一个对象**。所有记忆天然都属于它，写入与检索都**不需要**指定「谁」。
早期 MC 侧的 `companion_id` 字段已经删除；旧客户端继续传不会报错
（JSON 多余字段被忽略、query 参数被忽略），但值不再有任何作用。

### 1.2 `channel` —— 在哪发生的

| 值 | 用于 |
| --- | --- |
| `mc` | Minecraft 里的事 |
| `qq` | QQ 群聊 |
| `live` | 直播弹幕 |
| `system` | 系统自己产生的（日记生成、回滚审计） |

**这个字段决定两件事**：① 检索时的渠道可信度权重（MC 1.0 / QQ 0.9 / 直播 0.8）；
② 你以后能回答「这条记忆是从哪来的」。

> 弹幕可信度最低是刻意的：直播间里有玩笑、梗、反串，
> 而 MC 里亲历的事件是直接的。同样一句「玩家说 X」，从弹幕听到和亲眼看到不该同权。

### 1.3 `at_ms` —— 什么时候

**现实 UTC 毫秒时间戳**，这是全系统唯一的时间主轴。

- 不填 = 服务端用当前时间
- 跨渠道排序、时效衰减、日记窗口**全部**按它算
- 如果你有游戏内时间（比如 MC 的 `g<day>`），**不要**塞进 `at_ms`，
  用可选的 `channel_day` 字段作为标签传

> 为什么强调：游戏时钟和现实时钟不能混。MC 停服时 `dayTime` 不走，
> 一个周末现实过 2 天、游戏日只进 2 天，混用会让「昨天说的话」变成「上个月」。

## 2. 鉴权

```
X-API-Token: <token>
```

**只走 Header，不要拼进 URL**。URL 会进 nginx/CDN/代理的访问日志，
token 拼进去等于泄露。

| 情况 | 行为 |
| --- | --- |
| 服务端没配 token | 只监听 `127.0.0.1`，**外部根本连不上** |
| 配了 token | 监听内网，所有 `/v1/*`（除 `/v1/health`）要求 header |
| token 不对 | `401` |

只有 `/v1/health` 免鉴权，因为它只返回计数、不含任何记忆内容。

### 浏览器后台是另一套凭据

`/` 和 `/api/admin/*` 归**管理后台**，用会话 cookie（登录页拿的）。
它**不能**替代 API token——后台的 cookie 调 `/v1/*` 照样 401。

你对接时用 `X-API-Token` 就够了，不用管后台那套。

## 3. 写入

### 3.1 `POST /v1/event` —— 记一件发生过的事

```json
{
  "channel": "mc",
  "kind": "task.done",
  "summary": "盖好了小屋的东墙",
  "importance": 0.85,
  "at_ms": 1793085937278,
  "dedup_key": "mc-2026-10-27-wall-east",
  "person_id": "p-gleam",
  "scope": "companion",
  "channel_day": "g1024"
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `channel` | ✅ | `mc` / `qq` / `live` / `system`，未知值报 400 |
| `kind` | ✅ | 你自己的事件类型，自由字符串（`task.done`、`player.talked`…） |
| `summary` | ✅ | 一句话，不能全空白。**这条会进提示词**，写清楚点 |
| `importance` | | `[0,1]`，默认 0.5。越界报 400 |
| `at_ms` | | 不填 = 现在 |
| `dedup_key` | | **强烈建议填**，见 §3.3 |
| `person_id` | | 涉及的人，见 §5 |
| `scope` | | `player` / `companion` / `shared` / `world`，默认 `companion` |
| `channel_day` | | 仅 MC：游戏日标签，存着但**不参与排序** |

响应：

```json
{"id": 7, "duplicate": false}
```

`duplicate: true` 表示 `dedup_key` 已存在，这次被忽略了（`id` 为 `null`）。

### 3.2 `POST /v1/fact` —— 记一条「相信的事」

事件是「发生过什么」，事实是「它认为什么」。区别在于事实会被**取代**。

```json
{
  ,
  "channel": "mc",
  "key": "主人爱吃的",
  "value": "鱼",
  "importance": 0.8,
  "tier": "curated",
  "scope": "player",
  "person_id": "p-gleam"
}
```

| 字段 | 说明 |
| --- | --- |
| `key` / `value` | 事实的键与值。检索时渲染成 `key: value` |
| `tier` | `curated`（人写的） / `extracted`（模型推断的） |
| `expires_ms` | 过期时间，过了就不再被检索到 |
| `id` | 不填自动生成。**填了就是 upsert**（同 id 覆盖） |

> **`tier` 很重要**：`curated` 的事实**不随时间衰减**。
> 人亲手写下的事实不该因为放久了就变淡，而模型猜出来的可以。

响应：

```json
{"id": "f-1793086177293-1179adb8", "replaced": false}
```

### 3.3 `dedup_key` —— 为什么必须填

**QQ/弹幕断线会重放，MC 也会重试。** 没有幂等键，几万条里会混进重复事实，
而且这种重复**极难事后发现**——内容一样、时间相近，看起来就是「说了两遍」。

规则很简单：**同一次事件永远生成同一个 key**。

```
mc-<日期>-<事件摘要哈希>
qq-<群号>-<message_id>        ← QQ 的天然幂等键
live-<房间号>-<弹幕id>         ← 弹幕的天然幂等键
```

重放时服务端会返回 `duplicate: true`，不会写第二行。

## 4. 读取

### 4.1 `GET /v1/recall` —— 取记忆给提示词用

```
GET /v1/recall?topk=5&q=钻石
```

| 参数 | 说明 |
| --- | --- |
| `topk` | 返回几条，默认 8，上限 100 |
| `q` | 查询词。**空 = 按权重取最重要的几条**；非空 = 关键词匹配 |

真实响应：

```json
[
  {
    "kind": "event",
    "id": "6",
    "at_ms": 1793086117278,
    "text": "在 y=-54 发现了钻石矿脉",
    "weight": 0.8999200124446146,
    "why": "权重最高"
  },
  {
    "kind": "fact",
    "id": "f-1793086177293-1179adb8",
    "at_ms": 1793086177293,
    "text": "主人爱吃的: 鱼",
    "weight": 0.8,
    "why": "权重最高"
  }
]
```

**`why` 字段只有两个取值**（这是契约，不要按字面匹配之外的方式理解它）：

- `权重最高` = 没命中，纯兜底进来的
- `关键词命中` = 真的相关

想知道**具体命中了哪些词**，看同一行的 `matched` 数组（按贡献从大到小）：

```json
{"kind":"journal","hit":true,"score":1.0,"why":"关键词命中",
 "matched":["蜘蛛","蜘","蛛"], "text":"做完了「找蜘蛛摸线」"}
```

**`score` 与 `weight` 是两件事**：`weight` 只由重要性/时效/渠道决定，与提问无关；
`score` 才回答「这条有多切题」。排序是 `(hit, score, weight, at_ms)`，
所以切题优先于重要性。

> **检索方式：中文 BM25（bigram），不是子串匹配，也不是向量。**
>
> 旧版是 `contains(q)`，自然语言提问几乎必然查不到（实测 8 个改写提问命中 0/8）。
> 现在是字级 2-gram + BM25：`蜘蛛刷出来没有` 能命中 `做完了「找蜘蛛摸线」`。
> 中英文都按小写比，全角折半角。
>
> 仍然**不是语义检索**：同义词、跨语言（问「diamond」找「钻石」）查不到。
> 那要向量模型，是另一次改动 —— 现在的取舍是「一个二进制 + 一个 .db」，
> 实测真实库（752 条 / 2.6 万字符）上 p50 **0.74 ms**。

### 4.2 `GET /v1/event/list` —— 按时间列事件

```
GET /v1/event/list?limit=50
```

返回带 `weight` 的列表，按 `at_ms` 倒序。用于面板和调试，
**不要**拿它当检索（它不排序、不筛关键词）。

### 4.3 `GET /v1/health` —— 探活（免 token）

```json
{
  "ok": true,
  "app": "蓝鲸记忆中枢",
  "version": "0.1.0",
  "schema_version": 1,
  "uptime_ms": 279373,
  "bind": "0.0.0.0:25590",
  "loopback_only": false,
  "writes": 11,
  "dedup_hits": 0,
  "wal_bytes": 387312,
  "tables": [["person", 1], ["event", 7], ...],
  "latest_snapshot_ms": 1793086140175,
  "forgotten_rows": 0
}
```

只返回计数，**不返回任何记忆内容**——所以它才敢免鉴权。

`loopback_only: true` 表示当前只听本机（通常是没配 token）。

## 5. 身份：跨渠道「谁是谁」

### 5.1 为什么需要它

| 渠道 | 稳定 id |
| --- | --- |
| MC | 玩家 UUID（且 `online-mode=false` 时由名字派生） |
| QQ | QQ 号 |
| 直播 | 平台 uid |

**三套 id 天然不通。** 不解决这个，「QQ 里记得 MC 的事」就是假的——
系统不知道「QQ 上说话的人」和「MC 里那个人」是同一人。

### 5.2 `POST /v1/person/bind`

```json
{
  "channel": "mc",
  "account": "uuid-gleam",
  "person_id": "p-gleam",
  "seen_name": "Gleam"
}
```

响应：

```json
{
  "ok": true,
  "channel": "mc",
  "account": "uuid-gleam",
  "person_id": "p-gleam",
  "previous_person": null
}
```

- `person_id` 不存在会自动创建（`pending` 状态）
- 绑定即置为 `confirmed`
- `previous_person` 是**改绑时的旧归属**，用来追溯
- 同一个 `(channel, account)` 再绑一次就是改绑

### 5.3 `GET /v1/person/pending`

列出还没确认归属的账号，用于「把这两个账号拖到一起」。

### 5.4 `POST /v1/name/normalize` —— 把场景称呼换成显示名

同一个人在不同场景叫法不同（MC 名 / QQ 私聊昵称 / QQ 群名片 / 直播间昵称），
但两处会打架：**记忆与人格里用的是身份显示名**，模型在群里看到的却是群名片。
调用方在把回复发出去之前过一下这个接口，同一段话里就不会出现两个名字。

```bash
curl -X POST http://<主机>:25590/v1/name/normalize \
  -H "X-API-Token: <token>" -H "Content-Type: application/json" \
  -d '{"text":"啥子猫说得对","scene":"qq_group"}'
```

```json
{"ok":true,"text":"姆姆说得对",
 "replacements":[{"from":"啥子猫","to":"姆姆","count":1}]}
```

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `text` | ✅ | 要改写的文本，上限 4000 字 |
| `scene` | | `mc` / `qq` / `qq_group` / `live`。省略 = 所有场景的称呼都换 |

规则（都有测试钉住）：

- 只换 **2 个字以上**的称呼（单字几乎一定是误伤）；
- 称呼等于显示名时不换；
- 人工设置优先，没填就用渠道账号/群名片推导出来的值；
- **同一个称呼指向两个人时整条不换**——宁可漏换，不能张冠李戴；
- 长名字先换（不然「啥子猫」会被「啥子」先吃掉一半）。

> 它只改写文本，不改库里任何数据。调用方不调它也能正常收发，只是名字不会统一。

### 5.5 未绑定的账号怎么办

**照常记记忆，只是不跨渠道合并。** 每个新账号自动建一个 `pending` 的 person。
等人工绑定后，两边记忆**自动合并**——因为记忆挂的是 `person_id`，不是渠道 id。

> **绑定必须人工确认，不要自动猜。** 同名不代表同人。
> 猜错会把两个人的记忆混成一个人，而且**不可逆**。

## 6. 快照与回滚

### 6.1 `POST /v1/snapshot`

```json
{"note": "发版前"}
```

```json
{"id": 1, "taken_ms": 1793086140175, "path": "...", "bytes": 184320,
 "rows": 11, "sha256": "3639e2c4...", "note": "发版前"}
```

服务本身**每天自动拍一份**（每小时检查，同一天只拍一次）。
手动拍是给「我要做危险操作了」用的。

### 6.2 `POST /v1/rollback` —— 忘掉某时刻之后的记忆

```json
{"target_ms": 1793086000000, "note": "回到昨天"}
```

```json
{"rollback_id": 1, "target_ms": 1793086000000,
 "affected": [{"table": "event", "rows": 5}], "total": 5}
```

**边界是严格大于**：恰好等于 `target_ms` 的记录**保留**（那份快照里就有它）。

### 6.3 `POST /v1/rollback/undo` —— 撤销回滚

```json
{"rollback_id": 1}
```

回滚是**逻辑删除**，不是物理删除。撤销能把那次忘掉的全部恢复。
多次回滚可以逐层撤销，**乱序撤销也能工作**（每行只认自己那次 id）。

彻底清理（不可逆）由运维侧 `purge` 执行，没有 HTTP 接口——
这是刻意的：把不可逆操作放在网上是个坏主意。

## 7. 接入示例

### 7.1 Java（Minecraft 插件）

```java
// 用 JDK 自带的 HttpClient，不要引新依赖
var http = java.net.http.HttpClient.newHttpClient();

void remember(String summary, double importance) {
    String body = """
        {"channel":"mc","kind":"activity",
         "summary":"%s","importance":%s,"dedup_key":"mc-%d-%s"}
        """.formatted(esc(summary), importance, System.currentTimeMillis(),
                      Integer.toHexString(summary.hashCode()));

    var req = java.net.http.HttpRequest.newBuilder()
        .uri(java.net.URI.create(BASE + "/v1/event"))
        .header("X-API-Token", TOKEN)
        .header("Content-Type", "application/json")
        // 超时要比 tick 预算短：记忆写失败不能卡住游戏
        .timeout(java.time.Duration.ofMillis(500))
        .POST(java.net.http.HttpRequest.BodyPublishers.ofString(body))
        .build();

    // 异步发，不要阻塞服务端线程
    http.sendAsync(req, java.net.http.HttpResponse.BodyHandlers.discarding())
        .exceptionally(e -> { log.warn("记忆写入失败: {}", e.toString()); return null; });
}
```

**三条注意**：

1. **绝不能阻塞服务端线程**。用 `sendAsync`，而且失败只记日志，不影响游戏。
2. **超时要短**（≤500 ms）。记忆是锦上添花，卡住 tick 是灾难。
3. **`dedup_key` 必须稳定**。同一件事重试要用同一个 key。

### 7.2 Python（AstrBot / 弹幕机器人）

```python
import aiohttp, hashlib

async def remember(session, summary, *, channel="qq", importance=0.5, key=None):
    key = key or f"{channel}-{hashlib.md5(summary.encode()).hexdigest()[:12]}"
    payload = {
        "channel": channel, "kind": "message",
        "summary": summary, "importance": importance, "dedup_key": key,
    }
    async with session.post(f"{BASE}/v1/event", json=payload,
                            headers={"X-API-Token": TOKEN},
                            timeout=aiohttp.ClientTimeout(total=2)) as r:
        if r.status == 401:
            raise RuntimeError("token 不对")
        return await r.json()
```

QQ 的天然幂等键就是 `message_id`，直接用：

```python
await remember(session, content, channel="qq",
               key=f"qq-{group_id}-{event.message_obj.message_id}")
```

## 8. 常见问题

**Q：写失败了要重试吗？**

看响应里的 `retryable` 字段（错误响应带）。`storage`/`io` 类值得重试，
`bad_request` 重试永远是错的。

**Q：可以并发写吗？**

可以。服务端写是串行的（SQLite 只有一个写者），但吞吐实测
**5,700–7,400 次/秒**，p50 不到 4 ms。你不会成为瓶颈。

**Q：读会不会被写阻塞？**

不会。WAL 模式下读不阻塞写、写不阻塞读，读走独立连接池。
实测读 **7,700–8,300 次/秒**。

**Q：`importance` 该怎么给？**

先给直觉值，别纠结。它会乘上时效衰减和渠道可信度。
一个参考：日常闲聊 0.3 / 玩家说了偏好 0.7 / 一起完成了什么 0.85 / 重要承诺 0.95。

**Q：`summary` 要多长？**

一行，别超 100 字。它会被拼进提示词，太长会挤掉别的记忆。

**Q：能不能不传 `at_ms`？**

能，服务端用当前时间。但**补录历史数据时必须传**，否则所有历史都会堆在「现在」，
时效衰减就废了。

**Q：多台机器能共享同一个库吗？**

**不能共享 `.db` 文件**——WAL 依赖共享内存，网络文件系统上会损坏。
多台机器只能通过这个 HTTP 接口访问同一台主机上的服务。

## 9. 错误响应格式

所有错误统一：

```json
{
  "error": "请求不合法：importance 必须在 [0,1]",
  "kind": "bad_request",
  "retryable": false
}
```

| HTTP | `kind` | 含义 |
| --- | --- | --- |
| 400 | `bad_request` | 参数不对，重试没用 |
| 401 | `unauthorized` | 没带或带错 token |
| 404 | `not_found` | 目标不存在（比如撤销一个不存在的回滚） |
| 409 | `rollback` | 回滚不能执行（比如目标时间在未来） |
| 503 | `storage` / `io` | 存储不可用，**可以重试** |
