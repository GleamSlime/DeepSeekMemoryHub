> 目标：把记忆从 MC 插件里抽出来，做成**一套独立服务**，让 MC 插件里的角色、QQ 群机器人、直播间弹幕机器人
> 共用同一份记忆，彼此「记得」对方渠道发生过的事；同时满足**快照 + 冗余备份**。

> **位置**：本文属于独立系统 `MemoryHub/`，不是 MC 插件的子模块。
> 文中的相对路径（`插件/AiNpc/...`、`服务端/...`、`shared/...`）**都相对仓库根 `MC_AI/`**，

## 0. 结论先行

七条判断，每条后面都有实测依据：

1. **不要用现成框架**（mem0 / Zep / Letta / cognee）。四个主流项目**全是 Python**（实测 star 67k/32k/32k/25k），
   接进来等于为 388 KB 数据拖一个 Python 运行时 + 它自己的数据模型，
   而本项目的语义（手帐/日记/承诺/情绪）已经定型且经过打磨。**它们解决的是多租户 SaaS 的问题。**

2. **Rust 侧写「薄服务 + SQLite」，暂时不上向量库。** 实测真实库 **388 KB / 12 张表**，
   年增约 **12 MB**（journal 3.7 万条/年）。这个量级下 `rusqlite` + SQLite FTS5 完全够。
   上了 lancedb/qdrant 会让部署从「一个二进制 + 一个 .db」变成「还要起个服务」。

   > **修正（来自调研）**：`sqlite-vec` 连「后路」都算不上稳妥——它是 **pre-v1**（0.1.9 稳定 / 0.1.10-alpha），
   > 官方明说会 breaking。真需要语义检索时它仍是首选（唯一嵌入式方案），但要接受 API 会变。
   > **本项目当前 `fact` 表只有 10 行**，语义检索根本没有素材，先不做。

3. **【最高优先级 · 与迁移无关的存量风险】SQLite 版本带着一个已确认的 WAL-reset bug。**
   官方文档实测确认：影响 3.7.0–3.51.2，修复在 **3.51.3**。本项目 Java 侧用 `sqlite-jdbc:3.44.1.0`（含 bug），
   `rusqlite 0.32` 自带 3.46.0（含 bug）。**而本项目正好是「多进程共享同一个库」的拓扑**
   （`shared_dir` 已开、`.owner.lock` 正在被持有），正是官方说的触发条件。
   → 升级到 `sqlite-jdbc:3.51.3.0`（实测可下载）与 `rusqlite 0.41`（自带 3.54.1）。

4. **【已实证】直接拷 `memory.db` 会静默丢数据。** 实测此刻：主库 388 KB，**WAL 里还有 286 KB 未合并（占 74%）**。
   `cp memory.db` 后 `journal` 只有 **403** 条，而 `VACUUM INTO` 快照和真实库都是 **408** 条。
   **只拷主库会丢掉 5 条最新的、已提交的记录，而且没有任何报错。** 备份必须走 `VACUUM INTO`。

5. **真正的难点不是存储，是身份。** MC 玩家 = UUID（且 `online-mode=false`），QQ = QQ 号，两套 id 天然不通；
   现在 `player_names.json` 里**只有一条**手工映射。不先解决这个，「QQ 里记得 MC 的事」无法成立。（§4）

6. **时钟必须换成「现实时间为主轴」。** 现有规划日走游戏时钟 `g<day>`（`dayTime/24000`），
   QQ/直播**没有游戏时钟**。跨渠道共享时 `g<N>` 不能当全局时间轴。（§5）

7. **备份：`VACUUM INTO` 出一致快照 → restic 做多地冗余。主备份用 restic，
   `litestream` 先不用，`rustic` 明确不用。**（§6.4）
   - **不用 rustic**：官网自述 beta、不建议生产；与 restic 锁不兼容——在 rustic 写过的仓库上
     跑 `restic prune` **会删数据**。Rust 语言契合不是选它的充分理由。
   - **不用 litestream**：它是 Go 常驻进程，且恢复粒度比想象的粗（只能落在仍存在的 LTX 边界，
     L0 默认只留 5 分钟）。本项目 12 MB/年、100 条/天，`VACUUM INTO` 每 15 分钟一次，
     最坏丢 15 分钟记忆——**可以接受**，不值得为此多养一个服务。

> **一句话总览**：这次改造真正**新写**的只有两样——**身份映射**和**时钟统一**。
> 其余是把已有逻辑从 Java 搬到 Rust。**schema 不用重新设计**，
> 现有 12 张表（含 `dedup_key` 幂等、`expires_ms`、`superseded_by`）比多数开源框架更贴需求。

**而且本项目的 schema 已经赢过它们**：`fact` 的
`scope / tier / confidence / importance / expires_ms / superseded_by / vec`，
加上 `mood(PAD)` / `promise` / `diary` / `journal` / `self_narrative`——
**没有任何开源框架有对应的结构**。套进去只能全塞 metadata，检索时结构全丢。

> ⚠️ **两条时效性纠偏（网上大量教程已过时）**：
> ① `mem0ai/openmemory` **已不是**当年那个本地记忆 MCP 服务（现为 98★ 的 TS CLI），`mem0ai/mem0-mcp` **已 archived**；
> ② 嵌入式图数据库 **Kuzu 仓库已 archived（2025-10-10）**，Graphiti 自己也把它标 deprecated
> → 「用嵌入式图库」这条路**目前是空的**，这是「不用图库」判断里最硬的一条。

**借鉴思想但不抄代码**：graphiti 的「双时态」（事实带有效期）+ episode 溯源，设计上确实贴
「它记得谁何时说过什么」。代价是必须养图库，不划算。**记下这个概念即可。**

**图数据库要不要？不要。** 「记忆之间有关系」在这里是**一跳**关系
（`fact.subject_id` / `relation` / `promise`），SQL JOIN + 递归 CTE 就够。
需要图库的是多跳推理 + 社区摘要，那是刷 LongMemEval 分的场景，不是「它记得上周谁帮它修过屋顶」。

## 4. 【核心】身份模型

> **这一节决定成败。** 解决不了，其它做得再好都没意义。

### 4.1 问题

| 渠道 | 稳定 id | 现有映射 |
| --- | --- | --- |
| MC | `PlayerUUID`（`online-mode=false`，由名字派生） | `player_names.json`：**只有 1 条** |
| QQ | QQ 号 | 无 |
| 直播 | 平台 uid | 无 |

现状的硬伤：`qq_message.sender_uin` 存了 QQ 号，但 `relation` 表只按 `player_uuid` 索引
→ **QQ 上的人根本没有「关系」这条线**。

### 4.2 方案：`person` + `person_account` 两层

```sql
CREATE TABLE person (
  person_id    TEXT PRIMARY KEY,   -- 稳定内部 id（p-0001），永不变
  display_name TEXT NOT NULL,      -- 主显示名，提示词用这个
  status       TEXT NOT NULL,      -- pending / confirmed
  created_ms   INTEGER NOT NULL,
  note         TEXT
);

CREATE TABLE person_account (
  channel       TEXT NOT NULL,     -- mc / qq / live
  account       TEXT NOT NULL,     -- UUID / QQ号 / 平台uid
  person_id     TEXT NOT NULL REFERENCES person(person_id),
  seen_name     TEXT,              -- 该渠道上的名字（会变）
  first_seen_ms INTEGER NOT NULL,
  last_seen_ms  INTEGER NOT NULL,
  PRIMARY KEY (channel, account)
);
CREATE INDEX person_account_person ON person_account(person_id);
```

**绑定必须人工确认，不自动猜。** 同名不代表同人，猜错比不做更糟。三个入口：
1. `/ainpc person bind <渠道:账号> <person_id>`
2. QQ 侧「我是 MC 上的 Gleam」→ 机器人回口令 → 另一侧批准
3. `/usage` 页「记忆 / 身份」子页，把未绑定账号拖到一起

**未绑定账号照常记录**：每个新账号自动建一条 `person(status=pending)`，记忆挂 `person_id`。
绑定后两边记忆**自动合并**（因为都挂 person_id），不会丢数据。

### 4.3 迁移映射

| 现有 | 新 |
| --- | --- |
| `relation.player_uuid` | `person_id`（经 `person_account` 查） |
| `qq_message.sender_uin` | `person_account(channel='qq')` |
| `player_names.json`（1 条） | 1 个 person + 1 个 mc 账号 |

## 5. 【核心】时钟模型

### 5.1 冲突（已核实）

| 用途 | 现在 | 问题 |
| --- | --- | --- |
| 规划日 `planningDayId` | **游戏时钟** `g<day>` | QQ/直播**没有** `dayTime` |
| 日记窗口 | **现实时钟**（04:00 日界） | 与规划日不是一回事 |
| `at_ms` | 现实时间戳 | ✅ 对 |

### 5.2 方案

```
所有记忆条目：at_ms（UTC 毫秒）      ← 唯一主轴，三渠道都有
             + channel（mc/qq/live）  ← 来源
             + channel_day（可选）    ← 仅 MC：g<N>，存标签，不用于排序
```

- 排序/窗口/衰减**一律走 `at_ms`**
- `g<N>` 的语义**保留在 MC 渠道内**（plan 文件里），不进 Hub 通用字段
- QQ/直播的「今天」= 现实日（沿用日记的 04:00 日界）

### 5.3 为什么不是「给 QQ 编假游戏日」

MC 停服时 `dayTime` 不走。一个周末现实过 2 天、游戏日只进 2 天，两边窗口越错越远，
最后「昨天说的话」在记忆里变成「上个月」。**这是必须避免的。**

## 6. 备份（含本机实证）

### 6.1 实证：直接拷库会静默丢数据

**本次实测，2026-10-27 12:0x**：

```
主库 memory.db  = 388 KB
WAL  memory.db-wal = 286 KB   ← 占主库 74%，尚未合并

cp memory.db → journal 403 条   ❌
VACUUM INTO  → journal 408 条   ✅
真实库读     → journal 408 条   （基准）
```

**拷主库丢了 5 条最新记录，且没有任何报错。** 这就是为什么必须用 `VACUUM INTO`。

> 权威依据（已抓取原文）：SQLite 官方 WAL 文档 §4——
> 「WAL 文件是数据库持久状态的一部分，数据库被复制或移动时必须与 WAL 一起保留。
> 如果数据库文件与 WAL 分离，先前已提交的事务可能丢失，或数据库文件可能损坏。」

#### 6.1.1 WAL 文件大小 ≠ 未合并数据量（实测修正）

**先纠正一个容易犯的误判。** 在真实环境压测时观察到 WAL 稳定在 4.1 MB，
第一反应是「checkpoint 被长读事务饿死了」。**用 `PRAGMA wal_checkpoint(TRUNCATE)` 实测**：

```
busy=0  wal_log_pages=0  checkpointed=0   ← 剩余待合并 = 0
```

**数据其实早已全部合并进主库**。SQLite 的 checkpoint 是**覆盖** WAL 文件、
把写指针转回开头，**并不截断文件**（官方 wal.html §6 明说：
"checkpoint does not normally truncate the WAL file... it merely causes SQLite
to start overwriting the WAL file from the beginning"）。

所以：**WAL 文件大小是历史高水位，不是待处理积压。** 用它当「checkpoint 是否健康」
的指标会误报。真正该看的是 `wal_log_pages - checkpointed`（剩余页数）。

**结论与做法**：

1. 不要用 `-wal` 文件大小当告警阈值。要看 `PRAGMA wal_checkpoint` 的返回。
2. `Db::checkpoint()` 提供 `wal_checkpoint(TRUNCATE)`，**在拍快照前调用**——
   把 WAL 合并干净，`VACUUM INTO` 要拷的增量更小、更快。
3. `wal_autocheckpoint` 设为 512 页（约 2 MB，默认是 1000 页）。
   这是**写放大与读延迟的取舍**：WAL 小一半，读更快，代价是 checkpoint 更频繁。

#### 6.1.2 `VACUUM INTO` 的另一个副作用

- **需要约 2 倍库大小的空闲磁盘**。本项目 388 KB 可忽略，
  但库长到 GB 级后这条会变成限制。

> ⚠️ 长读事务**确实**会阻止 checkpoint 跑完（官方 §6）。这条是真的，
> 只是「WAL 文件大」不能用来证明它发生了——必须查 `wal_checkpoint` 的返回值。

**结论**：本项目规模下这些都不构成问题，但要写进运维手册——
**换到任何更大的数据集时它们会立刻变成问题。**

### 6.2 【新增 · 与迁移无关的现存风险】SQLite WAL-reset bug

**官方原文（已抓取 sqlite.org/wal.html §11）**：
- 影响版本：**3.7.0 (2010) 至 3.51.2 (2026-01-09)**
- 修复版本：**3.51.3 (2026-03-13)**；backport：3.44.6、3.50.7
- 触发条件：**同一文件有两个以上连接在不同线程/进程同时写或 checkpoint**

**本项目的情况（实测）**：

| 侧 | 当前版本 | 是否含 bug | 修复版 |
| --- | --- | --- | --- |
| Java 插件 | `sqlite-jdbc:3.44.1.0` | ❌ **含** | `3.51.3.0`（实测可下载，14.4 MB） |
| Rust Hub | `rusqlite 0.32` → 3.46.0 | ❌ **含** | `rusqlite 0.41` → 3.54.1（实测） |

**而且本项目正是官方说的触发拓扑**：`shared_dir` 已开启，`.owner.lock` 被持有，
意味着多个 MC 服务端进程共享同一个库文件。

> 官方评估概率低（「不高于 SSD 故障或宇宙射线」），但代价是**数据库损坏**，
> 且升级成本只是改两个版本号。**建议顺手升掉。**

### 6.3 两段式备份

```
memory.db
  └─(VACUUM INTO, 每 15 分钟)──> 一致快照（静止文件，可直接拷）
                                    └─(restic, 每小时/每天/每周)──> 本机 / 外置盘 / OSS / R2
```

**为什么必须分两段**：

- **第一段是正确性问题**：只有 `VACUUM INTO` 能拿到「事务一致」的副本（§6.1 已实证）。
  这一步之前，**任何文件级工具都是错的**。
- **第二段是冗余问题**：快照是静止文件，restic 才能安全地做去重、加密、增量、多地。

**两段之间是解耦的**：快照目录就是 restic 的源目录。换备份工具只影响第二段，
第一段的正确性不受影响。

> **为什么不用 litestream 补秒级**：见 §6.4.1，结论是**本项目不需要**。
> 在不用的前提下，RPO = 15 分钟（快照间隔）。

#### 6.4.1 litestream：要还是不要（两份调研的分歧，这里给结论）

两份调研对此**结论相反**，必须明说：

| 立场 | 理由 |
| --- | --- |
| 支持用 | RPO 秒级，防「刚聊完就宕机」；官方默认每秒同步 |
| **反对用** | 它是 **Go 独立进程**，为一个对象多养一个常驻服务；且**恢复粒度比想象的粗** |

**反对方的两条硬事实（都能查到官网原文）**：
1. **恢复只能落在仍存在的 LTX 文件边界**；L0 默认只留 **5 分钟**，之后最细退化到 L1 边界。
   回「三天前某个时刻」**根本做不到**，只能靠 restic 日快照。
2. 它接管 checkpoint，**只支持 WAL**，需要 `busy_timeout`；高写入时官方建议 `wal_autocheckpoint=0`。

**结论：本项目先不用 litestream。**

判定依据是我们自己的数字：**12 MB/年、约 100 条/天**。
这个量级下 `VACUUM INTO` 每 15 分钟一次的成本可以忽略，
**最坏情况丢 15 分钟记忆**——对一个「它记得上周谁帮它修过屋顶」的系统，这完全可以接受。

> **什么时候该回头加 litestream**：如果将来记忆写入频率涨到「每几分钟就有重要事件」，
> 或者你要拿它当正经的会话记忆后端。那时再评估，不要现在为假想需求多养一个进程。

**收益**：少一个常驻进程、少一套配置、少一个可能静默失败的点。这与「一个二进制 + 一个 .db」的部署目标一致。

### 6.5 保留策略（GFS）

| 通道 | 频率 | 保留 | 位置 | 验证 |
| --- | --- | --- | --- | --- |
| 快照 `VACUUM INTO` | **每 15 分钟** | 96 份（24h） | 本机 | 每小时验最新一份 `quick_check` |
| restic | 每小时 | 24 小时 | 本机 | 每周 `check` |
| restic | 每天 | 14 天 / 8 周 / 12 月 | **外置 SSD（离线）** | 每月 `check --read-data-subset=1/4` |
| restic | 每天 | 7 天 / 8 周 / 12 月 / 3 年 | 阿里云 OSS（内网 endpoint） | 每月 `1/8`；每季真恢复 |
| restic | 每周日 | 8 周 / 6 月 | Cloudflare R2（跨境） | 每半年 `--read-data` |

> **本项目的特殊优势**：库只有 **388 KB**、年增 12 MB。
> 这意味着「多发几份、多留几代」**成本几乎为零**——R2 免费额度 10 GB，
> 按年增 12 MB 算，**几十年也填不满**。所以保留策略可以比通用方案更宽松，不必抠存储费。

**三个落地细节**：① staging 与 repo 同盘；② staging 在 repo 外 + `--exclude`，备完即删；
③ `--keep-*` 按 host+paths 分组，**设好 `--group-by` 后不要改**，否则旧快照永不清理。

### 6.6 「备份是好的」怎么证明

**只有跑通恢复才算有备份。** 三层验证，第三层不可省：

| 层 | 手段 | 能证明什么 | 抓不到什么 |
| --- | --- | --- | --- |
| 1 | `PRAGMA integrity_check` | B-tree 结构自洽 | 内容对不对 |
| 2 | `restic check --read-data` | 字节没坏、没 bit rot | 内容对不对 |
| 3 | **业务断言 + 真起服务** | **这份备份能顶替生产** | — |

> **为什么第三层不可省**：前两层全是字节层。它们**都抓不到**「`VACUUM INTO` 一直在备份空库」
> 「备份路径写错、备的是三年前目录」「迁移后新库没纳入备份」——
> 这类事故的备份在字节层**完全健康**。

**恢复演练（每季，1 小时内）**：
1. 在**干净机器/容器**（不能是生产同盘）
2. 从 R2/OSS 拉最近快照
3. `integrity_check` + `foreign_key_check`
4. 业务断言：`count(*)` 不许减、`max(at_ms)` 不许更旧、关键表存在、最近事件可读
5. **用恢复数据真把服务起起来**：`/health` 200、能读出一条完整对话
6. 记 RTO 写进 `drills.md`
7. **结果写进 `/usage` 页「备份」区块**——判据是「不敲指令、连上服务就能看到上次演练时间与结果」

### 6.7 告警：要「死人开关」，不要「失败邮件」

**最常见故障是脚本根本没跑**（重启/盘没插/任务被卸载）——没有失败事件就永远没有邮件。
所以反过来：**成功了才发信号，没信号就报警**（healthchecks.io 这类）。

**restic 退出码必须分级看**：`0` 成功、`1` 致命、**`3` 部分是读不到→创建了不完整快照，必须当失败**、
`10` 仓库不存在、`11` 拿不到锁、`12` 密码错。只看「非零」会攒下一堆"成功"的不完整快照。

**macOS 用 launchd 而不是 cron**（cron 在睡眠/未登录时不触发）。

**再加一条新鲜度检查**：抓「天天成功但一直备份空目录」——退出码永远是 0，只有新鲜度会响。

**外置盘那条要加前置判断**：盘没插时**必须报 fail，而不是沉默跳过**。
最容易发生的失败是「盘拔了半年没人发现」，而脚本每天「成功」。

**五条通道分开建 check**，不要合并成一个「备份成功」——
合并之后某一条死了你永远不会知道是哪条。

### 6.8 云存储（针对中国大陆）

| 用途 | 载体 | 依据 |
| --- | --- | --- |
| 小时级/日级 | 本机 + **阿里云 OSS** | restic 原生支持 OSS（内网 endpoint 流量不计费） |
| 周级小体积 | **Cloudflare R2** | egress 免费、10 GB 免费额度；本项目 12 MB/年，**$0** |

**关键操作**：① OSS 走**内网 endpoint**（`oss-cn-xxx-internal`），流量不计费；
② 跨境**降并发**（抖动时降并发比加并发有效）；③ 跨境**不要设「每天必须成功」**，
设「本周成功一次即通过」——天天报警最后你会关掉所有告警，那才是真正的风险。

**必须接受的取舍**：国内云+跨境云双写引入新单点=**你的账号**（欠费/风控）。
所以三套独立密码、凭据至少一份在机器外、**外置 SSD 必须离线**（唯一不受账号影响的副本）。

> **未验证**：B2/AWS S3 官方价格表（JS 渲染未抓到）、`restic check --read-data` 的具体耗时。
> 不作断言。

## 7. 服务形态与协议

### 7.1 边界

```
┌──────────────────────────────────────────────────┐
│  Memory Hub（Rust，独立进程，:25590）             │
│  person / fact / relation / promise              │
│  event / journal / diary / self_narrative        │
│  mood / affect_log / trait                       │
│  qq_message / live_message                       │
│  + 检索 API（返回渲染好的上下文块）                │
└──────────────────────────────────────────────────┘
     ▲                ▲                ▲
  HTTP/JSON        HTTP/JSON        HTTP/JSON
  MC 插件(Java)    AstrBot(Py)      直播机器人(待建)
```

**留在 MC 本地**：坐标、`placed/`、`inventory/`、`shots/`、`transcripts/`、`usage/`

### 7.2 协议：REST/JSON 做唯一真相面，MCP 只做可选门面

| 方案 | 结论 |
| --- | --- |
| **REST/JSON** | ✅ **主面**。三个渠道都好接（Java HttpClient / Python aiohttp / curl 可调） |
| MCP | 🟡 **可选门面**，不是内部协议（理由见下） |
| gRPC | ❌ 两个调用方是脚本语言，protobuf 代码生成是纯负担 |

**为什么 MCP 不做内部协议**：

- MCP 的适用场景是「**模型自己决定**要不要调某个工具」。
  我们三个前端的调用时机**全是确定性的**：被点名 → 必须 recall；收到消息 → 必须 recall。
  不存在「模型琢磨要不要检索」的空间。
- 把 MCP 当内部协议 = 多一层 JSON-RPC 编解码，**同时丢掉** HTTP 天然的幂等、重试、鉴权表达。
- 现实依据：graphiti 的 reference MCP server **自己就不鉴权、不防注入**（README 自述）。
  这说明「用 MCP 解决服务间鉴权」是没先例的路。

**MCP 什么时候才值得加**：当你要**在 Claude Desktop / 其他外部 agent 里直接读这份记忆**时。
那时用 `rmcp 3.8.0` 起第二个 listener，作为**只读门面**，不碰内部契约。

> ⚠️ **绝不要让 MC 插件侧实现 MCP 客户端**：Forge 1.20.1 + Java 17 上官方 Java SDK 的适配情况
> **未验证**，而插件已有成熟的 HTTP 客户端 + token 口径（`:25585`）。多加一个 JSON-RPC 栈是纯风险。

**关键边界**：给**模型**看的工具（`remember`/`recall`）仍走 MC 现有 tool calling，
Hub 只是背后的存储。**不要把 Hub API 暴露给模型。**

### 7.3 API 草案

```
# 写入
POST /v1/event      {channel, account, at_ms, type, summary, importance, scope, dedup_key}
POST /v1/fact       {channel, account, subject, key, value, tier, confidence, importance}
POST /v1/qq/ingest  {messages:[...]}     # 沿用现有契约，AstrBot 只需改 base_url
POST /v1/message    {channel, account, content, at_ms, dedup_key}

# 读取
GET /v1/context?person=&channel=&lane=&query=&budget=600
    → **已渲染、已按预算裁剪**的文本块，渠道直接塞进提示词
GET /v1/recall?q=&topk=8
GET /v1/diary?kind=day&limit=1
GET /v1/health          # 含 schema 版本、备份状态

# 管理
POST /v1/person/bind  {channel, account, person_id}
GET  /v1/person/pending
```

> **`/v1/context` 返回渲染好的文本、而不是结构化数据**——这样三个渠道拿到的东西完全一致，
> 预算裁剪逻辑**只有一份**，不会出现「QQ 记得、MC 忘了」这种因算法不同导致的不一致。

#### 7.3.1 幂等键：每个写入口都必须有

**QQ/弹幕断线会重放，MC 也有重试。没有幂等键，几万条里会混进重复事实**，
而且这种重复**极难事后发现**（内容一样、时间相近，看起来就是「说了两遍」）。

好消息：现有 `event` 表**已经把这个机制做好了**，照搬即可：

```sql
dedup_key TEXT
CREATE UNIQUE INDEX event_dedup ON event(dedup_key) WHERE dedup_key IS NOT NULL;
```

**要求**：每个写入口都带 `(channel, source_id, dedup_key)`。
- MC：沿用现有 `EventRecorder` 的 key 规则
- QQ：用 `message_id`（现有 `qq_dedup` 唯一索引已是这个思路）
- 直播：平台弹幕 id

#### 7.3.2 检索：三路合并，不是纯向量

```
结构化过滤（subject_id / scope / status / expires_ms）
        ↓
   vec0 KNN top-50        （有向量时）
        ↓
   FTS5 / BM25 top-50     （中文需分词）
        ↓
   去重 → 按「重要性 + 新鲜度 + 是否亲历」加权排序
```

**为什么不是纯向量**：
- **当前 `fact` 只有 10 行**，语义检索没有素材；数据结构化程度很高（谁、何时、什么 scope）
- 纯向量会把 `expires_ms` 已过期、`status=superseded` 的旧信念也检索出来
- **排序权重必须能自己调**（重要性、新鲜度、是否亲历），这是任何框架都不给的

> **未验证**：`tantivy-jieba` 与 `tantivy 0.27` 的耦合情况。
> 先用 SQLite 内置 FTS5，需要时再上 tantivy + `jieba-rs`。

### 7.4 鉴权

沿用现有已验证模型：回环免 token；非回环必须 `X-API-Token` **Header**（不拼 URL，URL 会进访问日志）；
**不同渠道发不同 token**（`mc_token`/`qq_token`/`live_token`），一个泄露不影响其它，且能按渠道审计。

## 8. 并发模型

沿用 `CompanionStore` 已被验证的结论：**一个写线程，队列有界，满了就丢并记日志**。

> 现有注释原话：「记忆丢一条比卡住主线程好」。Hub 里同理——超时 200 ms 返回「记忆暂不可用」。

⚠️ **Rust 特有陷阱**：`rusqlite` 是同步的，**绝对不能在 async 任务里直接调用**（会阻塞整个 executor）。
写走 `tokio::sync::mpsc` 单通道 + 一个专属写任务；读走 `spawn_blocking`。

## 10. 风险与待决

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| **SQLite WAL-reset bug** | 数据库损坏 | ✅ 升级到 3.51.3 / 3.54.1（§6.2） |
| **拷库丢数据** | 备份不可用且无报错 | ✅ 强制 `VACUUM INTO`（已实证，§6.1） |

### 10.1 一个需要明确接受的设计取舍

**「先在 MC 本地写、再同步 Hub」意味着双写期存在短暂不一致。**
这不是 bug，是刻意换来的**可回退性**——Hub 出任何问题，MC 都能照常工作。

代价要说清：**双写期如果对账不认真，两边的数据会静默分叉**。
所以阶段 2 的判据里有「跑 24h 两边条数一致」，且要有对账工具。

### 已定：部署做成「可迁移」

> **用户 2026-10-27 拍板**：「还没定，先做成可迁移的」。

这条决策对设计的实际影响（不是一句口号）：

1. **Hub 只认配置，不认路径**：数据目录、监听地址、端口全部走配置文件 / 环境变量，
   **代码里不出现任何绝对路径**。
2. **不做任何「本机特化」**：不依赖 macOS 专有 API（`tmutil`、APFS 快照）。
   备份调度抽象成「外部命令 + 配置」，macOS 用 launchd、Linux 用 systemd timer，
   两者都只是调同一个脚本。
3. **不用 litestream**（§6.4.1）在这个决策下更正确——少一个平台相关的常驻进程。
4. **SQLite 单文件 + `VACUUM INTO` 是天然的迁移单元**：换机器 = 拷一个 `.db` + 一份配置。
   **这正是选 SQLite 而不是 PG/Neo4j 的另一个收益**，不只是「简单」。
5. **跨机器时的硬约束**：`WAL` **不能用于网络文件系统**（wal-index 依赖共享内存，
   所有进程必须同机）。所以「数据放 NFS，多台 MC 共享」这条路**从根上是错的**——
   多台机器共享记忆**只能通过 Hub 的 HTTP 接口**，不能共享 .db 文件。

### 仍需用户拍板

1. **直播平台是哪个？**（B 站 / 抖音 / 其它）—— 决定阶段 6 可行性
2. **跨渠道隐私边界**：QQ 群里说的话，要不要让**所有人**都能通过 MC 里的它问出来？
