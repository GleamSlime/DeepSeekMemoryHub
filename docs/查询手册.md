
> **单主体设计（schema v7 起）**：中枢是**一个人的**记忆，不是多人的。
> 所有接口里原来的 `companion_id` 字段/参数**已删除**——旧客户端继续传不会报错
> （JSON 多余字段被忽略、query 参数被忽略），但它的值**不再有任何作用**。
> 表上统一为 `owner_id`，固定值 `me`，不参与筛选。

## 1. 必须先知道的三件事

### 1.1 哪条是「有效」的记录

除了 `person`/`person_account`/`mood` 这类状态表，**几乎所有表都有一个 `deleted_by` 列**：

| `deleted_by` | 含义 |
| --- | --- |
| `NULL` | **当前有效**，正常检索能看到 |
| 有值（数字） | 被某次回滚「遗忘」了，数据**还在**，只是不出现 |

**所以查询几乎永远要带 `WHERE deleted_by IS NULL`。**
忘了带，你会看到「明明回滚过却还在」的假象。

想看被遗忘的：`WHERE deleted_by IS NOT NULL`。

### 1.2 时间是什么单位

`at_ms`、`created_ms`、`updated_ms` 都是 **UTC 毫秒时间戳**。

```sql
-- 转成本地时间看
datetime(at_ms/1000, 'unixepoch', 'localtime')

-- 反过来：查某个本地时间之后的事件
at_ms > strftime('%s','2026-10-27 15:00:00','utc')*1000
```

> ⚠️ 注意 `'utc'` 修饰符：`strftime` 默认按本地时间解释字符串，
> 加 `'utc'` 才是「这个本地时间对应的 UTC」。

### 1.3 事实有「历史版本」

`fact` 表里同一个 `key` 可能有多行：

| 状态 | 含义 |
| --- | --- |
| `superseded_by IS NULL` | 当前有效 |
| `superseded_by` 有值 | 被新版本取代的**旧版本**，留着回答「它以前是这么想的」 |

同一 `(**已废弃**, person_id, key)` 同时只有一个有效版本。
查到多条同名 key 时，看 `superseded_by` 分辨新旧，**不要当成重复 bug**。

## 2. 场景化查询（最常用）

### 2.1 「它怎么不记得我说过的话？」

```bash
DB=~/MemoryHub/data/store/memory.db
NPC=大肥鱼

# ① 这个 NPC 有没有收到过那条事件
sqlite3 -header -column "$DB" "
  SELECT id, datetime(at_ms/1000,'unixepoch','localtime') t, kind,
         substr(summary,1,60) summary
  FROM event
  WHERE  AND deleted_by IS NULL
    AND summary LIKE '%钻石%'
  ORDER BY at_ms DESC;"

# ② 有没有进手帐（手帐才是计划与日记的输入）
sqlite3 -header -column "$DB" "
  SELECT id, type, substr(summary,1,60) summary, importance
  FROM journal
  WHERE  AND deleted_by IS NULL
    AND summary LIKE '%钻石%';"
```

**判断链**：事件表有、手帐没有 → 被重要度门槛筛掉了（看 `journalImportanceMin`）；
两边都没有 → 根本没写进来，去查接入方。

### 2.2 「检索（recall）为什么没返回它？」

```bash
# 直接调接口看真实结果
TOKEN=$(cat ~/MemoryHub/data/.token)   # 或服务端配的 BLUEEWHALE_TOKEN
curl -s -H "X-API-Token: $TOKEN" \
  "http://127.0.0.1:25590/v1/recall?topk=10&q=钻石" \
  | python3 -m json.tool
```

返回里每条有 `weight`、`score`、`why`、`matched`：

- `why = 关键词命中` → 匹配上了
- `why = 权重最高` → 没命中关键词，是按权重进来的
- `score` → 相关度 (0,1]，0 表示纯兜底
- `matched` → 具体命中了哪些词（如 `["蜘蛛","蜘","蛛"]`）

**注意 `weight` 和 `score` 不是一回事。** `weight` 只看重要性/时效/渠道，
与提问无关；问「蜘蛛」时它不会变。`score` 才回答「这条有多切题」。
如果检索结果看起来跟提问无关，先看 `score` 是不是 0 ——
是 0 就说明这批全是兜底行，也就是「什么都没想起来」。

**检索是中文 BM25，不是子串匹配。** 所以 `q=蜘蛛刷出来没有` 能命中
`做完了「找蜘蛛摸线」`，但同义词查不到（问「diamond」找不到「钻石」）。

**权重算不出来？** 手动复算：

```bash
curl -s -H "X-API-Token: $TOKEN" http://127.0.0.1:25590/v1/stats \
  | python3 -c "import json,sys; print(json.load(sys.stdin)['weight_config'])"
```

公式（`docs/架构方案.md` §3.2）：

```
weight = importance^exp × 衰减(半衰期) × 强化(回忆次数) × 渠道可信度
```

常见「为什么它排不上」：`importance` 给低了 / 太老（衰减）/ 渠道是 `live`（可信度 0.8）。

### 2.3 「情绪怎么是空的 / 怎么是这个情绪？」

```bash
DB=~/MemoryHub/data/store/memory.db

# 当前状态（注意：库里存的是最后一次被推动时的值，
# 接口返回的才是补算过衰减的「现在」）
sqlite3 -header -column "$DB" "SELECT * FROM mood;"
```

正确做法是查接口，它会补算衰减：

```bash
curl -s -H "X-API-Token: $TOKEN" \
  "http://127.0.0.1:25590/v1/mood?" | python3 -m json.tool
```

情绪只被**特定 kind** 推动，见 `src/affect.rs` 的 `delta_for`：

| kind | 效果 |
| --- | --- |
| `task.done` / `task_done` | 愉悦↑ 唤醒↑ 支配↑ |
| `attacked` / `damage` | 愉悦↓ 唤醒↑↑ 支配↓ |
| `task.failed` | 愉悦↓ 支配↓ |
| `discovery` / `player.together` / `gift.received` | 正面 |
| 其它 kind | **不推动** |

所以「情绪没变化」多半是事件 `kind` 不在表里。

### 2.4 「它今天打算做什么？/ 计划为什么没执行？」

规划在**两张表**里，注意别只查一张：

```bash
DB=~/MemoryHub/data/store/memory.db

# 最近 5 份规划
sqlite3 -header -column "$DB" "
  SELECT planning_day_id 游戏日,
         date(created_ms/1000,'unixepoch','localtime') 创建,
         (SELECT COUNT(*) FROM plan_item i WHERE i.plan_id=p.id) 总,
         (SELECT COUNT(*) FROM plan_item i WHERE i.plan_id=p.id AND state='done') 完成,
         substr(summary,1,40) 摘要
  FROM plan p WHERE deleted_by IS NULL
  ORDER BY created_ms DESC LIMIT 5;"

# 某份计划的具体条目（按原顺序，不要按 id 排）
sqlite3 -header -column "$DB" "
  SELECT ord, title, task_type, state, substr(coalesce(outcome,''),1,30) 结果
  FROM plan_item
  WHERE plan_id = (SELECT id FROM plan WHERE planning_day_id='g1')
  ORDER BY ord;"

# 全库的条目状态分布
sqlite3 -column "$DB" "SELECT state, COUNT(*) FROM plan_item GROUP BY state;"
```

**两个坑**：

1. **`planning_day_id` 是游戏日 `g<N>`，不是日期**。它只作标签，排序一律用
   `created_ms`（现实时间）。游戏时钟在停服期间不走，拿它排序会把
   「最近一份」判错。
2. **一条都没执行**？看 `state`：
   - `deferred` = 暂缓（**不是完成，也不是失败**，条件满足会自动打勾）
   - `dropped` = 主动放弃
   - `todo` = 还没轮到
   `outcome` 字段写着实际发生了什么。

> 规划原本**不在 SQLite 里**，是 `plans/<npc>/g<N>.json` 独立文件。
> 如果你只跑了 `migrate --from`（数据库迁移），规划是空的——必须加
> `--plans <目录>` 才会迁。

### 2.5 「是不是有重复数据？」

```bash
DB=~/MemoryHub/data/store/memory.db

# 重复事件（同一 dedup_key 多行）——正常情况下唯一索引会挡住
sqlite3 -header -column "$DB" "
  SELECT dedup_key, COUNT(*) n FROM event
  WHERE dedup_key IS NOT NULL GROUP BY dedup_key HAVING n>1;"

# 重复事实（同一 key 多个有效版本）——正常应为空
sqlite3 -header -column "$DB" "
  SELECT **已废弃**, key, COUNT(*) n FROM fact
  WHERE deleted_by IS NULL AND superseded_by IS NULL
  GROUP BY **已废弃**, key HAVING n>1;"
```

第二条如果**有输出**，说明写入走了绕过 supersede 的路径（比如直接改库），
可以用 `PATCH /v1/fact/{id}` 或重新 POST 修正。

### 2.6 「回滚之后数据还在？」

**这是设计如此**，不是 bug。回滚是逻辑删除。

```bash
# 看有哪些被遗忘但还在的
sqlite3 -header -column "$DB" "
  SELECT 'event' t, COUNT(*) n FROM event WHERE deleted_by IS NOT NULL
  UNION ALL SELECT 'fact', COUNT(*) FROM fact WHERE deleted_by IS NOT NULL
  UNION ALL SELECT 'journal', COUNT(*) FROM journal WHERE deleted_by IS NOT NULL;"

# 看回滚历史（谁在什么时候忘了什么）
sqlite3 -header -column "$DB" "
  SELECT id, datetime(at_ms/1000,'unixepoch','localtime') t,
         datetime(target_ms/1000,'unixepoch','localtime') rolled_to,
         mode, note
  FROM rollback_log ORDER BY id DESC;"
```

撤销某次回滚：`curl -X POST -d '{"rollback_id":N}' .../v1/rollback/undo`

### 2.7 「快照是不是好的？」

```bash
# 命令行体检（推荐，一条看全部）
~/MemoryHub/target/release/bluewhale-memory doctor

# 或直接验一个快照文件
sqlite3 ~/MemoryHub/data/store/snapshots/snapshot-XXXX.db "PRAGMA quick_check;"
```

`quick_check` 返回 `ok` 才算好。**只有文件在那儿不算。**

### 2.8 「跨渠道的人怎么没对上？」

```bash
DB=~/MemoryHub/data/store/memory.db

sqlite3 -header -column "$DB" "
  SELECT p.person_id, p.display_name, p.status,
         GROUP_CONCAT(a.channel||':'||substr(a.account,1,12), ' | ') accounts
  FROM person p LEFT JOIN person_account a ON a.person_id=p.person_id
  GROUP BY p.person_id ORDER BY p.created_ms DESC;"
```

`status = pending` 表示还没确认归属 → 记忆不会跨渠道合并。
绑：`POST /v1/person/bind {"channel":"qq","account":"12345","person_id":"p-xxx"}`

## 3. 直接改数据（谨慎）

> ⚠️ **服务运行时不要用 sqlite3 直接写库。**
> 服务持有写连接，外部写会撞 `database is locked`，或绕过业务逻辑（比如不写 `dedup_key`）。
> **要改数据，用 HTTP 接口或先进后台面板。**

### 3.1 接口改（推荐）

```bash

```


## 4. 性能：查询慢怎么办

```bash
# 看查询计划（有没有走索引）
sqlite3 "$DB" "EXPLAIN QUERY PLAN
  SELECT * FROM event WHERE  ORDER BY at_ms DESC LIMIT 10;"
```

`SCAN` = 全表扫（4 万条以内还行）；`SEARCH ... USING INDEX` = 走索引。

现有索引（`sqlite_master` 可查全）：

| 表 | 索引 | 用途 |
| --- | --- | --- |
| event | `event_recent` | 按 NPC + 时间倒序 |
| event | `event_dedup` | 幂等键去重 |
| event | `event_live` | 只查有效记录 |
| fact | `fact_lookup` | 按 NPC + 人 + 状态 + key |
| journal | `journal_recent` | 按 NPC + 时间 |

**`LIKE '%关键词%'` 用不到索引**（前导通配符）。几千条内无所谓，
上万条后要改成 FTS5。当前规模不必优化。

## 5.5 迁移后的数据怎么核对

从 MC 旧库迁过来之后，要能确认「迁全了、没迁重」。

```bash
OLD=~/MC_AI/shared/deepseek_mc/memory.db     # 旧库
DB=~/MemoryHub/data/store/memory.db          # 新库

# 逐表对比行数
for t in "event:event" "journal:journal" "diary:diary" "fact:fact" \
         "self_narrative:self_narrative" "mood:mood" "persona_trait:trait"; do
  old="${t%%:*}"; new="${t##*:}"
  a=$(sqlite3 "$OLD" "SELECT COUNT(*) FROM $old;" 2>/dev/null || echo 0)
  b=$(sqlite3 "$DB"  "SELECT COUNT(*) FROM $new;" 2>/dev/null || echo 0)
  printf "%-16s 旧库 %-6s 新库 %-6s\n" "$old→$new" "$a" "$b"
done
```

迁移是**幂等**的：重复跑不会产生重复行（靠源库 id 或 `dedup_key`）。
所以「新库比旧库少」不对，但「新库比旧库多」是正常的（新库可能还有迁移后新产生的数据）。

```bash
# 抽查一条迁移过来的记录（手帐 id 是原样保留的）
sqlite3 -header -column "$DB" "SELECT id, summary FROM journal WHERE id='j1';"

# 确认没有重复
sqlite3 "$DB" "SELECT COUNT(*) FROM (
  SELECT id FROM journal GROUP BY id HAVING COUNT(*)>1);"   # 应为 0
```

**迁移前会自动拍一张快照**，迁错了用 `rollback --to <那张快照的时间>` 撤销。

## 8. 一条命令看全（贴进 shell 就能用）

```bash
bw-doctor() {
  DB=${1:-$HOME/MemoryHub/data/store/memory.db}
  echo "=== 数据库 $DB ==="
  command -v sqlite3 >/dev/null || { echo "需要 sqlite3"; return 1; }
  [ -f "$DB" ] || { echo "文件不存在"; return 1; }
  echo "--- 大小 ---"; ls -lh "$DB"* 2>/dev/null | awk '{print $5, $9}'
  echo "--- 完整性 ---"; sqlite3 "$DB" "PRAGMA quick_check;"
  echo "--- 行数 ---"
  sqlite3 -column "$DB" "SELECT 'event',COUNT(*) FROM event WHERE deleted_by IS NULL
    UNION ALL SELECT 'fact(有效)',COUNT(*) FROM fact WHERE deleted_by IS NULL AND superseded_by IS NULL
    UNION ALL SELECT 'journal',COUNT(*) FROM journal WHERE deleted_by IS NULL
    UNION ALL SELECT 'diary',COUNT(*) FROM diary WHERE deleted_by IS NULL
    UNION ALL SELECT 'person',COUNT(*) FROM person
    UNION ALL SELECT '被遗忘',COUNT(*) FROM event WHERE deleted_by IS NOT NULL;"
  echo "--- 最近事件 ---"
  sqlite3 -column "$DB" "SELECT datetime(at_ms/1000,'unixepoch','localtime'),
    channel, substr(summary,1,44) FROM event WHERE deleted_by IS NULL
    ORDER BY at_ms DESC LIMIT 5;"
  echo "--- 情绪 ---"; sqlite3 -column "$DB" "SELECT **已废弃**,label,
    round(valence,2),round(arousal,2),round(dominance,2) FROM mood;"
}
# 用法： bw-doctor ~/MemoryHub/data/store/memory.db
```
