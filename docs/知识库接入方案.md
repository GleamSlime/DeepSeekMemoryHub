# 知识库（Knowledge Base）接入方案

> 状态：**已实施（2026-10-30）**。代码在 `src/kb/`，接口 `/v1/kb/*`。
> 阶段 1–4 完成；阶段 5（面板页）未做，阶段 6（并入 `/v1/context`）按建议**刻意未做**。
> 日期：2026-10-30
> 范围：在记忆中枢里新增一个**独立于 NPC 记忆**的知识库子系统
> 前置条件：一个 OpenAI 兼容（`POST /v1/embeddings`）的嵌入服务
> 已知限制：**没有重排序（rerank）模型**，只有嵌入模型

---

## 0. 结论先行

七条判断，每条后面都有实测依据或明确取舍。

1. **知识库是独立体系，不复用 `event` / `journal` / `fact`。**
   理由不是"干净"，是**生命周期完全不同**：记忆会衰减、会过期、会被取代、要能回滚；
   知识库的条目是**外部资料**，不衰减、不随时间变淡、回滚它没有语义。
   混在一张表里，`weight` 模型和回滚逻辑会把它当成记忆去处理，两头都不对。

2. **不需要分块（chunking）。** 实测现有语料：`journal` 平均 **26 字**、`event` 36 字、
   最长 206 字。知识库的条目按段落/小节存即可。**128K 上下文的嵌入模型配一个
   512 token 的分块器，是把简单问题复杂化。** 只有当单个知识条目超过模型上下文时
   才需要切分，那时也要按**语义边界**（标题、空行）切，不按固定字数。

3. **"没有 rerank" 是这个方案里唯一真正要设计的事。**
   实测当前 BM25 的分数分布：查「箱子」命中 **208 条**、查「鱼竿」**237 条**，
   而最终只需要 5 条。第 1 名 1.472、第 6 名 1.266 —— **分差极小，靠分数截断等于随机**。
   rerank 的作用正是"从 50 条里挑 5 条"，没有它就必须用别的东西补这段。

4. **替代 rerank 的是「RRF 融合 + 分组去重」**（见 §5）。
   **实测**（780 条语料 / 45 条查询）：纯 BM25 的 MRR 是 0.398，
   加向量并用 RRF 融合后是 **0.500**，逐条比较 **24 胜 10 负** —— 语义检索的收益是实的。
   而**加权和反而是四种融合里最差的**（MRR 0.441），第一版的猜测被自己的实测推翻。
   > 「互证加分」这个我原本设计的信号**删掉了**：加了没有可测量的收益，
   > 只多两个要调的参数。

5. **嵌入服务是软依赖。** 服务不可用 → 自动退回纯字面检索，
   **不报错、不降级返回空**。这与既有的「Hub 停掉时 MC 照常工作」是同一套风格。

6. **首次引入对外网络依赖，二进制会变大。** 现在主依赖里**没有** HTTP 客户端
   （`reqwest` 只在 `dev-dependencies`，测试用）。
   **实测**（2026-10-30，`opt-level=3` + `lto=thin` + `strip`，最小可运行程序）：
   - 无依赖基线：**0.34 MB**
   - `reqwest + rustls-tls + json + tokio` 且真实发一次请求：**2.78 MB**
   - → **净增约 2.4 MB**，中枢会从 5.6 MB 变成 **约 8 MB**
   这是本项目"一个二进制 + 一个 .db"原则的第一次让步，要明确接受。
   （可以再省：用 `ureq`（阻塞式，无 tokio 集成）能更小，但会和现有
   `spawn_blocking` 模型打架，不值得。）

7. **向量存储先用 BLOB + 暴力扫描，不上向量库。**
   现有语料 800 条量级。1024 维 f32 = 4 KB/条，全量 800 条 = 3.2 MB 内存。
   **实测**（`rustc -O` 单线程纯点积，2026-10-30）：800 条 = **1.01 ms**，
   5,000 条 = 3.53 ms，50,000 条 = **30.55 ms**。上 sqlite-vec / lancedb 是过早优化
   （且 `sqlite-vec` 是 pre-v1，官方说会 breaking）。
   **触发换索引的判据**：条目 > 50,000 **或** 单次检索 > 50 ms（见 §8）。

## 1. 为什么知识库不能是记忆

这是本方案最重要的一条边界。不是洁癖，是四件具体的事会出错：

| 维度 | 记忆（现有三表） | 知识库（新增） |
| --- | --- | --- |
| **时效** | 有半衰期衰减（30 天），老记忆让位给新的 | **不衰减**。一份设定文档三年前写的和三年前一样真 |
| **失效** | `expires_ms` / `superseded_by` / `deleted_by` 回滚 | 只有"这一版覆盖上一版"，没有"忘了它"这回事 |
| **权重** | `importance × 衰减 × 强化 × 渠道可信度` | `importance` 概念不成立。一条资料不因为"被想起来的次数少"而变不重要 |
| **来源** | 三渠道（MC/QQ/直播），渠道可信度不同 | 单一来源：人喂进去的文档。没有可信度差异 |

如果把知识库塞进 `fact` 表（它已经有 `vec` 列），后果是具体的：

- 知识条目会被 30 天半衰期衰减掉，用户会看到"喂的资料慢慢变淡了"——**而这是静默的**
- `note_recalled` 会给它累加 `recall_count`，让热门条目永久霸榜
- 回滚「忘掉某时刻之后的记忆」会把资料一起抹掉——**这不是用户的意思**
- `/v1/context` 的预算丢弃顺序（从下往上丢）会先丢掉知识库段，而资料恰恰是最稳定的那段

**所以：新表、新接口、独立的检索路径。**

## 2. 数据模型

### 2.1 表

```sql
-- 一个知识库（可以有多本：MC 设定 / 服务器规则 / 世界观 ...）
CREATE TABLE IF NOT EXISTS kb (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  description TEXT,
  created_ms  INTEGER NOT NULL,
  updated_ms  INTEGER NOT NULL
);

-- 一篇文档（对应一个文件 / 一个网页 / 一段粘贴的文本）
CREATE TABLE IF NOT EXISTS kb_doc (
  id          TEXT PRIMARY KEY,
  kb_id       TEXT NOT NULL REFERENCES kb(id),
  title       TEXT,
  source      TEXT,          -- 文件名 / URL / "paste"
  content_hash TEXT NOT NULL, -- 内容指纹：同一份文档重复导入时幂等
  n_chunks    INTEGER NOT NULL DEFAULT 0,
  created_ms  INTEGER NOT NULL,
  updated_ms  INTEGER NOT NULL,
  deleted_by  INTEGER
);
CREATE UNIQUE INDEX IF NOT EXISTS kb_doc_hash ON kb_doc(kb_id, content_hash)
  WHERE deleted_by IS NULL;

-- 检索单元。**不是固定字数切出来的块**，是语义边界切出来的段落
CREATE TABLE IF NOT EXISTS kb_chunk (
  id          TEXT PRIMARY KEY,
  doc_id      TEXT NOT NULL REFERENCES kb_doc(id),
  kb_id       TEXT NOT NULL,
  ord         INTEGER NOT NULL,   -- 在文档内的顺序，用于取上下文与排序稳定
  heading     TEXT,               -- 所在小节标题（有就带上，检索时一起算分）
  text        TEXT NOT NULL,
  -- 向量。维度由 embedder 决定，**不同 embedder 的向量不可比较**。
  vec         BLOB,
  vec_dim     INTEGER,
  vec_embedder TEXT,
  -- 嵌入状态机：pending / done / failed / skipped
  embed_state TEXT NOT NULL DEFAULT 'pending',
  embed_tries INTEGER NOT NULL DEFAULT 0,
  embed_err   TEXT,
  created_ms  INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS kb_chunk_doc     ON kb_chunk(doc_id, ord);
CREATE INDEX IF NOT EXISTS kb_chunk_pending ON kb_chunk(embed_state) WHERE embed_state = 'pending';
```

### 2.2 为什么 `vec_dim` 和 `vec_embedder` 都要存

这是从 MC 侧 `Embedder` 的注释里学到的、**必须照抄的一条**：

> 两个不同 embedder 产生的 384 维向量形状完全一样，不比较就看不出问题，
> 而打分会是垃圾。

所以：`vec_embedder` 或 `vec_dim` 与当前配置不一致的条目，**直接从检索候选里剔除**，
并在 `/v1/kb/health` 里报出数量。绝不"先比再说"。

### 2.3 为什么 `embed_state` 是个状态机

嵌入是外部调用，会超时、会挂、会返回 500。三种状态必须显式建模：

- `pending` — 待嵌入（新导入的条目）
- `done` — 已嵌入
- `failed` — 试过 `embed_tries` 次，都失败；`embed_err` 存最后一次的错误
- `skipped` — 明确不嵌入（比如嵌入功能整个关闭时的存量数据）

没有 `failed` 状态的话，一条永远嵌不进去的条目会被无限重试，
把每次回填都拖成一次全表扫描。**重试上限默认 5 次，超过就落 `failed` 并不再自动重试。**

## 3. 嵌入服务接入

### 3.1 协议

OpenAI 兼容，只用两个字段：

```http
POST /v1/embeddings
Authorization: Bearer <token，可选>
Content-Type: application/json

{"model": "...", "input": ["文本1", "文本2"], "dimensions": 1024}
```

响应：

```json
{"data": [{"index": 0, "embedding": [0.1, ...]}, {"index": 1, "embedding": [...]}]}
```

**必须按 `index` 归位**，不能假设返回顺序与请求一致。这是 OpenAI 兼容服务里
常见的静默陷阱：vLLM、TEI、llama.cpp 的实现细节不同，有的并发处理会乱序。
按 `index` 归位是一行代码的事，不按就是"向量和文本错配"，而且**永远不会有报错**。

### 3.2 配置

```toml
[kb]
enable = true
embed_url   = "http://192.168.3.252:11434/v1/embeddings"
embed_model = "qwen3-embedding:0.6b-q8"
embed_dim   = 512           # 实测 512 与 1024 质量差异在噪声内，存储省一半
embed_token = ""            # Ollama 本地不需要
embed_batch = 16            # 实测 16 一批合适
embed_timeout_seconds = 30  # 实测热查询 23ms，但冷加载与批量嵌需要余量
```

> **这些默认值不是拍的，是 2026-10-30 实测定的**（详见 §5.6）：
> 0.6B 与 8B 质量无显著差异（逐条14:17）、但快 5.2 倍省 3.6 倍内存；
> 512 维与 1024 维质量无显著差异、存储和计算各省一半。

对应环境变量 `BLUEWHALE_KB_*`，与既有配置风格一致。

#### `embed_dim` 到底是哪个数字

Qwen3-Embedding-0.6B 的规格里有**四个**容易混的数，这里一次说清：

| 数 | 含义 | 对知识库的影响 |
| --- | --- | --- |
| **0.6B** | 参数量（模型大小） | 决定显存/内存与推理速度，**与存储无关** |
| **32K** | 上下文长度（能一次读多少 token） | 决定要不要分块（本方案默认不切，见 §4） |
| **1024** | **向量维度 `embed_dim`** | **决定存储与计算**：每条 `dim × 4` 字节 |
| 28 | Transformer 层数 | 无需关心 |

`embed_dim` = 一段文本进去、出来那个 **float 数组的长度**。
Qwen3-Embedding-0.6B 默认输出 1024 维，且支持 MRL，可自定义到 **32~1024** 任意值。

三个直接后果：

1. **存储**：1024 维 = 4 KB/条；512 维 = 2 KB/条。5 万条分别是 200 MB / 100 MB
2. **计算**：暴力点积的耗时与维度成正比（实测 800 条：1024 维 1.01 ms，512 维 0.45 ms）
3. **必须全局一致**：查询向量和文档向量必须同维度、同模型。不一致 → 打分是垃圾且**零报错**，
   所以 `kb_chunk` 存 `vec_dim` + `vec_embedder`（§2.2）

#### 服务不支持 `dimensions` 参数时怎么办

`dimensions` 是 OpenAI 的扩展参数，**不是所有兼容实现都支持**（vLLM 支持、TEI 视版本、
llama.cpp 的 server 可能忽略它）。要分两条路：

- 服务支持 → 请求里带 `"dimensions": 512`，直接拿到 512 维
- 服务不支持 → 拿到模型默认的 1024 维，**客户端自己截断前 512 维 + 重新 L2 归一化**

第二条是可用的，因为 Qwen3-Embedding 支持 MRL（Matryoshka）：取前 k 维本身就是一个
合法嵌入。但**必须重新归一化** —— 截断会改变向量模长，不归一化会让 cosine 算错。

启动探针（§3.2）要顺便检测这件事：发一次带 `dimensions` 的请求，
看实际返回长度是否等于请求值，从而判断走哪条路。

**启动期校验**（不是等第一次检索才发现）：

- `enable=true` 但 `embed_url` 为空 → **拒绝启动**，报明确的配置错误
- `embed_dim` 不在 `[32, 8192]` → 拒绝启动
- 启动时做一次**探针调用**（嵌一个 `"ping"`）：
  - 成功 → 记下实际维度，与 `embed_dim` 不符则拒绝启动（维度错配是最难查的一类）
  - 失败 → **不阻止启动**，只打警告，检索自动走纯字面

### 3.3 降级

这是明确要求的行为，必须写死：

| 情形 | 行为 |
| --- | --- |
| 嵌入服务不可用 | 检索退回纯字面（BM25），**接口仍返回 200** |
| 查询嵌入超时 | 同上，并在响应里带 `"degraded": "embed_timeout"` |
| 条目未嵌入 | 该条目仍可被字面命中，只是不参与向量召回 |
| 全部条目都没嵌入 | 完全等价于现在的 BM25 行为 |

**降级必须是可观测的**，不能悄悄发生。所以：

- `/v1/kb/health` 返回 `pending` / `failed` / `embeddable` 计数与最近一次错误
- 每次检索响应带 `degraded` 字段（可用时省略）
- 日志里**只在状态翻转时**打 WARN（可用→不可用，反之亦然），不是每次失败都打

最后一条很重要：一个挂掉的服务如果每 3 秒打一行错误日志，日志就没用了。

## 4. 分块策略：**默认不切**

### 4.1 实测依据

现有语料长度（这条决定了要不要分块器）：

| 表 | 条数 | 均值 | 中位 | p95 | 最大 | >200 字 |
| --- | --- | --- | --- | --- | --- | --- |
| `journal` | 606 | 26 | 15 | 52 | 97 | 0 |
| `event` | 164 | 36 | 17 | 109 | 179 | 0 |
| `channel_message` | 46 | 45 | 15 | 155 | 206 | 1 |
| `diary` | 8 | 201 | 230 | 323 | 323 | 5 |

**记忆侧几乎没有长文本。** 知识库的资料会长一些，但嵌入模型上下文是
32K（Qwen3-Embedding-0.6B），一份几页的设定文档一次就能嵌完。

### 4.2 只在超长时才切，且按语义边界

```text
切分规则（按优先级）：
1. 整篇 ≤ max_chunk_chars（**默认 700 字**）  → 不切，整篇一个 chunk
2. 否则按 markdown 标题（# / ## / ###）切
3. 单个小节仍超长 → 按空行（段落）切
4. 单个段落仍超长 → 按句子切（。！？\n）
5. 单个句子仍超长 → 硬切（这是唯一会破坏语义的情形，要记日志）
```

**不做 overlap（重叠窗口）。** 重叠是为"固定字数切块会切断语义"准备的补丁；
按标题/段落切之后，这个补丁没有对应的问题，只会让同一段文字被重复召回，
在**没有 rerank** 的情况下尤其糟糕（同一段占掉多个 top-k 名额）。

### 4.2.1 为什么默认是 700 字，不是 2000

**这个数字是被「没有 reranker」反推出来的，不是常规值。**

rerank 缺席时，正确的代偿方式是**多给几条让下游自己挑**：

- 有 rerank：召回 50 条 → 精排 → 只塞 3~5 条进 prompt（每条可以很长）
- 没 rerank：召回 → 融合 → **塞 8~12 条进 prompt**，让 LLM 自己判断哪条有用

后者要求「同样的 token 预算里装进更多条」，所以每条得更短：

| 块大小 | 4000 字预算能塞几条 | 覆盖到几个不同事实 |
| --- | --- | --- |
| 2000 字 | 2 条 | 2 个（且每条大量冗余） |
| **700 字** | **5~6 条** | **5~6 个** |
| 300 字 | 13 条 | 13 个，但单条上下文可能不够 |

700 字是折中：一条能容纳一个完整小节（够 LLM 判断），又不至于让每条都塞满
无关内容。700 字对中文约 **400~500 token**，与业界常用的 256~512 token/块 同量级。

**这是与「没有 reranker」直接绑定的参数。** 将来接上 reranker 之后，
可以放心把它调回 1500~2000（因为精排能把噪声滤掉，长块提供的信息更完整）。

### 4.3 `heading` 单独存，并与正文一起算分

检索时把 `heading` 和 `text` 拼起来参与打分，但**分开存**：

- 存一起 → 面板上显示"这条命中了什么"会带一堆重复的标题
- 分开存 → 可以单独给 heading 加权（标题命中通常比正文命中更相关）

## 5. 【核心】没有 rerank 怎么办

### 5.0 先纠正一个容易得出的错误结论

**「没有 rerank，所以接知识库作用也不大」是错的，错在把两种不同量级的收益放在一起比。**

拆开看两件事：

| 变化 | 量级 |
| --- | --- |
| 从「没有任何外部资料」到「能语义召回」 | **0% → 70~85%**（recall@5，取决于语料） |
| 从「embedding 召回」到「embedding + rerank」 | **再 +5~10 个百分点** |

rerank 只影响**已召回集合内部的排序**，是二阶效应；而知识库解决的是
**「根本没有这条路」**，是一阶的。它的距离差一个数量级。

更具体地说，rerank 主要在三种情形下值钱：

1. **语料同质化严重**，大量候选近乎等价（这时排序几乎没有正确排序可言）
2. **必须把 50 条压到 5 条**（token 预算卡死）
3. **查询带约束**（「除了 A 以外」「比 B 早的」），双塔模型看不见否定和比较

**而这三条里，第 1 条恰恰是「现在的记忆库」的特征，不是「知识库」的特征。**

### 5.0.1 上一版这里用错了例子

上一版我写「查『箱子』命中 208 条、第 1 名 1.472 / 第 6 名 1.266，分差极小」，
并把它当成「没有 rerank 所以效果差」的证据。**这个例子是记忆库的，不是知识库的。**

实测记忆库的构成：

| 内容形态 | 占比 |
| --- | --- |
| `做完了「X」` 模板 | **55.6%** |
| `今天的打算/回顾` 长模板 | **40.4%** |
| 其余 | 4.0% |

**96% 是模板化内容。** NPC 每天重复做同样的事（理箱子、钓鱼、找蜘蛛线），
于是「箱子」真的对应 200 多条互不相同、但语义等价的记录。**分数挤在一起是
数据本身重复的必然结果，换任何检索方法都一样。**

知识库不是这种数据。它是一份份人写的资料，条目之间天然有区分度。
**把一个「日志去重」问题误当成「检索方法」问题，是我上一版的错。**

### 5.1 rerank 的职责，拆开看是两件事

**rerank 模型（cross-encoder）做的事，本质是两件：**

1. **精确相关性**：把 query 和 doc 拼起来一起过模型，能看到词序和依存关系
   —— 向量（双塔）看不到这个，因为 query 和 doc 是分别编码的
2. **候选压缩**：从 50 条里挑 5 条

第 2 件是"排序"，第 1 件是"更准的相似度"。**没有 cross-encoder，可以用
别的信号逼近第 1 件；第 2 件则靠融合与去重。**

### 5.2 四路信号，全部不依赖额外模型

| 信号 | 来源 | 补的是 rerank 的哪个职责 |
| --- | --- | --- |
| **A. 向量相似度** | `cosine(query_vec, chunk_vec)` | 语义泛化（同义、跨语言） |
| **B. 字面相关度** | 现有 `rank::Bm25` | 精确词命中（专有名词、编号、坐标） |
| **C. 标题命中** | `heading` 里出现 query 的词 | 精确相关性的替代品之一 |
| **D. 互证加分** | A 和 B **同时**命中的条目 | 候选压缩 + 置信度 |

**D 是没有 rerank 时最重要的一条**。它基于一个朴素的观察：

> 一条被"语义"和"字面"两路独立召回的条目，比只被一路召回的更可能是正确答案。

这不是玄学：两路召回的错误模式几乎不重叠（向量会错在"字面完全不同但主题相近"，
BM25 会错在"共享一个高频词但意思无关"）。两路都命中，错误概率相乘下降。

### 5.3 融合公式：用 RRF，**不要用加权和**

> ⚠️ **这一节在 2026-10-30 被实测推翻了一次。**
> 第一版写的是「加权和 0.5×向量 + 0.3×BM25 + 0.1×互证」，
> 并在旁边注了一句「权重是推的，不是实测的」。模型部署后实测下来，
> **那个加权和是四种融合方式里最差的一种**（详见 §5.6）。
> 现在改成 RRF，理由如下。

**加权和的问题**：BM25 分数与 cosine **不在同一个尺度上**，必须先各自归一化。
而归一化（除以本条查询的最高分）会让两者的相对权重随查询漂移 ——
某条查询里 BM25 最高分很低时，它的归一化结果会被抬成 1.0，
于是"弱证据"被当成"强证据"。这不是调参数能解决的，是方法选错了。

**RRF（Reciprocal Rank Fusion）只用排名，不用分数**：

```text
score(d) = w_vec / (k + rank_vec(d))  +  w_lit / (k + rank_lit(d))
k = 60（业界默认值，实测里没调过）
```

排名是天然同尺度的，所以不存在归一化问题。代价是丢掉了"分差有多大"这个信息
—— 但对本场景是好事，因为实测 BM25 的分差本来就不可靠（§5.0.1）。

**实测权重（冻结语料 780 条 / 45 条查询）**：

| 融合方式 | recall@5 | MRR |
| --- | --- | --- |
| 纯向量 | 64.4% | 0.481 |
| 加权和 0.5/0.3（原方案） | 57.8% | 0.441 |
| RRF k=60 等权 | 64.4% | 0.493 |
| **RRF k=60 向量×2** | **64.4%** | **0.500** |
| 并集（两路各 top5） | 64.4% | 0.479 |

**默认权重 `w_vec=2.0, w_lit=1.0`**（即向量排名更可信），k=60。

为什么向量权重给 2 倍：实测逐条对比里，向量独立赢 9 条、BM25 独立赢 6 条，
而向量赢的那些**赢得更大**（BM25 排 115 → 向量排 3、排 74 → 排 1），
BM25 赢的多是小胜（排 5 → 排 7 这类）。

**"互证加分"（原 §5.2 的 D 信号）被删掉了。** 它的想法不算错，
但实测在 RRF 之上再加它没有带来可测量的收益，反而多两个要调的参数。
**能少一个参数就少一个** —— 这个项目的教训已经够多了。

### 5.4 候选压缩：分组去重

没有 rerank 时，top-k 被同一篇文档的多个 chunk 占满是常见失败模式
（问一个主题，返回 5 条全都来自同一份文档的相邻段落）。

```text
1. 各路召回各自的 top-N（N = pool_size，默认 50）
2. 融合打分
3. 按 doc_id 分组，每组最多取 max_per_doc 条（默认 2）
4. 组内按 ord 相邻的合并成一条（把上一段/下一段拼上，给模型完整上下文）
5. 截断到 topk
```

第 3 步是关键。**没有 rerank 时，"多样性"比"绝对分数"更重要** ——
因为分数本身不可靠，5 条来自 5 个不同文档的结果，比 5 条来自同一文档更可能
有一条是对的。

### 5.5 不做的事

- **不做 query 改写**（用 LLM 把问题改写成多个查询）：那需要再调一个 LLM，
  延迟和成本都是数量级上升，而且在本项目里 LLM 是插件侧的事，中枢不该擅自调。
- **不做 HyDE**（让模型先生成假想答案再检索）：同上。
- **不自造 cross-encoder**：0.6B 的 reranker 也就 1.2 GB，等有了直接接，
  不要用启发式手搓一个近似品——那会带来一堆调不完的参数。

### 5.6 【实测】2026-10-30 的完整结果

**测试条件**

- 语料：真实记忆库冻结快照 `VACUUM INTO`，**780 条**（event 164 / journal 609 / fact 7）
- 查询：**45 条**手写中文查询，**刻意不含答案关键词**（否则测的只是字面匹配，那是 BM25 的主场）
- 真值：检索 top-k 里有任意一条含指定概念词即算命中
- 模型：`qwen3-embedding:0.6b-q8` / `4b-q4` / `8b-q4`，Ollama 在 `192.168.3.252:11434`
- 维度截断由 Ollama 的 `dimensions` 参数完成（实测会**自动重新 L2 归一化**，模长恒为 1.000000）

**主表**（融合方式 = RRF k=60 向量×2）

| 配置 | recall@1 | recall@5 | recall@10 | MRR |
| --- | --- | --- | --- | --- |
| BM25 单路（中枢现状） | 28.9% | 57.8% | 62.2% | 0.398 |
| **0.6b-q8** dim=1024 | 37.8% | 64.4% | 73.3% | 0.500 |
| **4b-q4** dim=1024 | 37.8% | 64.4% | 77.8% | 0.502 |
| **8b-q4** dim=1024 | 40.0% | 68.9% | 77.8% | 0.524 |

**逐条配对比较（比看聚合百分比可靠得多）**

| 对比 | 前者赢 | 后者赢 | 结论 |
| --- | --- | --- | --- |
| 0.6b-RRF **vs** BM25 | **24 条** | 10 条 | 语义检索**明确更好**，不是噪声 |
| 8b **vs** 0.6b | 14 条 | **17 条** | **8B 并没有更好** |

第二行是这次实测最重要的发现：**8B 的聚合 recall@5 更高（68.9% vs 64.4%），
但逐条比它输多赢少（14 : 17）。** 差的那 2 条查询（68.9% 与 64.4% 相差 2/45）
完全在噪声范围内，而代价是：

| | 0.6b-q8 | 4b-q4 | 8b-q4 |
| --- | --- | --- | --- |
| 单条查询延迟（热） | **22.7 ms** | 70.8 ms | 117.9 ms |
| 常驻内存 | **1.74 GB** | 3.74 GB | 6.35 GB |
| 嵌 780 条耗时 | **18 s** | 94 s | 167 s |

**所以选 0.6B。** 8B 慢 5.2 倍、占内存 3.6 倍，换来的差异落在噪声里。

> **注意量化不对等**：0.6b 是 **Q8_0**，4b/8b 是 **Q4_K_M**。
> 所以这张表**不能**用来证明"模型变大没有用"——它混了模型大小和量化两个变量。
> 能证明的只有一件事：**在当前部署里，0.6b-q8 是与 8b-q4 同等好且更省的选择。**
> 要公平比较大小，得拉 `4b-q8` / `8b-q8` 重测（8b-q8 约 8.5 GB）。

**维度：512 vs 1024（只测了 0.6b）**

| | recall@5 | MRR | 存储 | 暴力点积 |
| --- | --- | --- | --- | --- |
| dim=1024 | 64.4% | 0.500 | 4 KB/条 | 1.01 ms |
| dim=512 | 62.2% | **0.535** | **2 KB/条** | **0.45 ms** |

@5 差 1 条查询（噪声），MRR 反而 512 更高。**结论：用 512。**
存储省一半、点积快一倍，质量差异在噪声内。

**指令前缀（Qwen3-Embedding 是 instruction-aware 的）**

| | @1 | @5 | @10 | MRR |
| --- | --- | --- | --- | --- |
| 0.6b 裸查询 | 37.8% | 64.4% | 71.1% | 0.481 |
| 0.6b 带指令 | 33.3% | 57.8% | **77.8%** | 0.460 |

**结论：不加指令前缀。** @1/@5 略降、@10 略升，整体在噪声内。
加它还要多维护一份指令文案，不划算。

**这套评测本身的局限（必须知道）**

1. **45 条查询，1 条 = 2.2%**。差 1~2 条的任何结论都不可信
2. **真值是"概念词是否出现"**，不是人工标注的相关性等级。这会低估
   "答对了但用词不同"的检索，也会高估"撞上同词"的检索
3. **语料是记忆库，不是知识库**。96% 是模板化重复内容（§5.0.1），
   真实知识库的条目区分度更高，**向量方法的优势应该比这里更明显**
4. 查询是我写的，可能不自觉地偏向某种检索方式

**所以：上表的绝对数字只能横向比较，不要当"知识库的准确率"引用。**

## 6. 检索接口

### 6.1 `POST /v1/kb/search`

```json
// 请求
{
  "kb_id": "mc-lore",          // 可选，缺省=所有库
  "q": "蜘蛛线怎么弄",
  "topk": 5,                   // clamp [1, 20]
  "pool": 50                   // 可选，覆盖默认候选池
}

// 响应
{
  "hits": [
    {
      "chunk_id": "c-...",
      "doc_id": "d-...",
      "doc_title": "MC 生存指南",
      "kb_id": "mc-lore",
      "heading": "材料 · 蜘蛛线",
      "text": "……",
      "score": 0.83,
      "why": {
        "vec": 0.71,             // 向量相似度（未命中为 0）
        "lit": 0.55,             // 字面相关度
        "heading_hit": true,
        "agree": true            // 两路都命中
      }
    }
  ],
  "degraded": null,            // 降级原因，正常时为 null
  "pool_size": 50
}
```

`why` 照抄 `/v1/recall` 的可解释性承诺：**必须能回答"为什么这条排第一"**。
没有 rerank 时这一点更重要 —— 用户会怀疑排序，而`why` 是唯一的抓手。

### 6.2 `POST /v1/kb/doc`

导入一份文档（幂等，按 `content_hash`）：

```json
{"kb_id": "mc-lore", "title": "生存指南", "source": "guide.md", "content": "..."}
```

响应报出 `{doc_id, n_chunks, duplicate: bool}`。

**导入是同步的，但嵌入是异步的。** 理由：

- 导入要立刻可用（用户要能看到"导入成功了"）
- 嵌入要调外部服务，可能慢、可能挂 —— 不能让它阻塞导入
- 所以导入后条目是 `pending`，由后台任务回填（§7）

代价是：**刚导入的文档，几秒内只能被字面命中**。这个行为要写进文档，
否则用户会以为导入失败。

### 6.3 `/v1/kb/health`

```json
{
  "kb_count": 2,
  "doc_count": 37,
  "chunk_count": 412,
  "embed": {
    "state": "ok",            // ok / degraded / disabled
    "model": "Qwen3-Embedding-0.6B",
    "dim": 1024,
    "pending": 12,
    "failed": 0,
    "last_error": null,
    "last_ok_ms": 1793326812083
  }
}
```

## 7. 嵌入回填：后台任务

照抄 `spawn_daily_snapshot` 的形状：

```text
每 30 秒（可配）醒一次：
  1. 取 embed_state='pending' 且 embed_tries < 5 的条目，最多 embed_batch 条
  2. 没有 → 睡
  3. 有 → 一次请求嵌入，按 index 归位写回
  4. 失败 → embed_tries += 1，记录 embed_err
     · embed_tries >= 5 → 落 failed
     · 连续 3 批失败 → 退避（30s → 60s → 120s，上限 10 分钟）
  5. 成功 → 复位退避
```

**退避是必须的。** 没有退避时，一个挂掉的服务会被每 30 秒固定重试，
在日志里留下固定频率的错误，而且永远不会自愈到正常节奏。

**导入后主动催促一次**：导入新文档后立刻 wake 一次后台任务，而不是等下一个 30 秒。
这是"几秒内只被字面命中"那个窗口能有多短的唯一办法。

## 8. 什么时候该换掉暴力扫描

现在的方案是「全量 BLOB + 内存暴力点积」。明确写下触发条件，到点再换：

| 指标 | 阈值 | 依据 |
| --- | --- | --- |
| 条目数 | **> 50,000** | 50k × 1024 维 = 200 MB 内存，超出一个"轻服务"该占的量 |
| 单次检索耗时 | **> 50 ms** | 现有检索 p50 是 2.14 ms，再慢 20 倍就没法每轮对话都调 |
| 内存占用（RSS） | **> 500 MB** | 这是台 Mac mini/普通服务器，不是专用检索机 |

**到阈值时的选项（按推荐顺序）：**

1. `sqlite-vec` — 唯一嵌入式方案，但 **pre-v1，官方说会 breaking**，要接受 API 变
2. 自己写 IVF（k-means 分桶 + 桶内暴力）— 约 300 行，可控，但要做索引重建
3. `lancedb` / `qdrant` — 能力过剩，且让部署从"一个二进制"变成"还要起个服务"

**现在不做的理由不是"以后再说"，是"没有数据支持现在就做"。**
实测 800 条 × 1024 维暴力点积是 **1.01 ms**，加在现有 2.14 ms 的检索上是
3 ms 量级，可以接受。提前上 ANN 只会引入一个会 breaking 的依赖和一套需要维护的索引。

**但 50,000 条时已经是 30.55 ms** —— 这还没算上 BM25 那一路与融合打分的开销。
所以「条目数 > 50,000」这个阈值是和实测对齐的，不是拍脑袋：
到那时单次检索总耗时已经贴着 50 ms 的红线。

## 9. 改动清单

按实施顺序，每步都能独立验证：

### 阶段 1：schema 与存储（无外部依赖）

- `src/db.rs`：`SCHEMA_VERSION` 8 → **9**；新增三张表；`add_column_if_missing` 不需要（全新表）
  - 注意：`CREATE TABLE IF NOT EXISTS` 对**新表**是有效的，老库升级时会建上
- `src/kb.rs`（新）：领域模型 + CRUD（`Kb` / `KbDoc` / `KbChunk`）
- `src/kb/chunk.rs`（新）：§4 的切分器 + 单测（长文本、无标题、超长段落、空输入）
- 判据：建库、导文档、读回来、`content_hash` 幂等

### 阶段 2：检索（仍然无外部依赖，可先跑）

- `src/kb/rank.rs`（新）：§5 的融合打分 + 分组去重
  - **复用 `src/rank.rs` 的 `Bm25`**，不要写第二份
- `/v1/kb/search` 路由（向量那一路先恒为 0，纯字面也能工作）
- 判据：无嵌入时 = 纯 BM25 行为；分组去重生效；`why` 字段正确

### 阶段 3：嵌入客户端

- `Cargo.toml`：`reqwest` 从 dev-deps 提到主依赖（用 `rustls-tls`，不引 OpenSSL）
  - 体积：**已实测**净增约 2.4 MB（见 §0 第 6 条），中枢 5.6 MB → 约 8 MB。
    实施后要再量一次并更新这个数字
- `src/kb/embed.rs`（新）：OpenAI 兼容客户端
  - 按 `index` 归位（§3.1）
  - 超时、重试、降级（§3.3）
  - 单测用本地假服务器，**不打真实网络**
- 判据：假服务器返回乱序 → 归位正确；超时 → 降级不报错

### 阶段 4：回填任务

- `src/main.rs`：`spawn_kb_backfill`，照 `spawn_daily_snapshot` 的形状
- 判据：pending → done；失败累计 → failed；退避生效

### 阶段 5：接口与面板

- `/v1/kb/doc`、`/v1/kb/health`、`/v1/kb/list`
- 面板加「知识库」页：文档列表、条目数、嵌入状态、错误
  - 照现有面板风格（纯表单提交，不依赖 JavaScript 的部分要保持）

### 阶段 6：与 `/v1/context` 的关系（可选，**建议先不做**）

**建议第一版不要把知识库塞进 `/v1/context`。** 理由：

- `/v1/context` 的六段是**NPC 自我认知**（我在做什么、我记得谁、我什么心情）。
  外部资料不属于"我是谁"，塞进去会让模型分不清"我知道的事"和"我查到的资料"
- 段落顺序已经排满，加第七段的预算丢弃顺序要重新设计
- 更干净的做法：**插件在需要时主动调 `/v1/kb/search`**，
  拿到结果后自己决定怎么拼进 prompt

如果确实要做，段落名用 `kb`，插在 `memory` **之后**、`events` **之前**，
并在 `why`/`dropped` 里能看出它是知识库段。

## 10. 风险与待决

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **没有 rerank，top-5 质量不确定** | 用户可能觉得"查出来的不相关" | §5 的融合+互证；**模型部署后先跑一批真实查询做对比**，不要凭感觉调权重 |
| 维度/模型错配 | 打分成垃圾且无报错 | §2.2 存 `vec_embedder` + `vec_dim`，不匹配直接剔除 |
| 二进制变大 | 5.6 MB → 约 8 MB（实测净增 2.4 MB） | 接受；但**不引 OpenSSL**，用 `rustls` |
| 嵌入服务挂掉 | 检索退化 | §3.3 降级 + 可观测 |
| 首次导入很慢 | 用户以为卡住 | 导入同步、嵌入异步；`/v1/kb/health` 能看到 pending 数 |
| 知识库与记忆混淆 | 模型把资料当亲历 | 接口分开、`/v1/context` 默认不合并（§9 阶段 6） |

### 已由实测解答（2026-10-30）

| 原问题 | 结论 | 依据 |
| --- | --- | --- |
| `embed_dim` 取多少 | **512** | @5 差 1 条（噪声），MRR 512 反而更高（0.535 vs 0.500）；存储省一半、点积快一倍 |
| 用哪个模型 | **0.6b-q8** | 与 8b-q4 逐条 14:17（8B 并没有更好），但快 5.2 倍、省 3.6 倍内存 |
| 要不要指令前缀 | **不要** | @1/@5 略降、@10 略升，整体在噪声内，还多一份要维护的文案 |
| 融合方式 | **RRF k=60，向量×2** | MRR 0.500，比加权和的 0.441 高；加权和是四种里最差的 |

### 仍需你拍板的

1. **知识库只给谁用？** 只给 NPC 对话，还是也给面板搜索/给别的渠道？
   这决定要不要做 `/v1/kb/list` 的分页和过滤。
2. **要不要第一版就做导入文件/URL？** 建议只做 `POST /v1/kb/doc` 的
   "贴文本"，文件和 URL 抓取是另一个改动（编码检测、HTML 提取、重定向……）。
3. **要不要拉 `4b-q8` / `8b-q8` 做一次公平的同量化对比？**
   现在的 0.6b 是 Q8、4b/8b 是 Q4，混了量化变量。8b-q8 约 8.5 GB，
   要先确认那台机器的可用内存够不够。**不做也不影响上面的结论**
   —— 结论是"当前部署里 0.6b-q8 是最优"，这一点是成立的。

## 11. 与既有设计的对照

这套东西**不是**在推翻已有设计，是补上一直留着的那一格：

| 既有 | 这次的关系 |
| --- | --- |
| `fact.vec` / `vec_embedder` 列（2026-10-27 留下） | **空着没用**（实测 0/22 有条目）。方案 §2.2 沿用它"必须存 embedder id"的判断 |
| `src/rank.rs` 的 `Bm25` | **直接复用**，不写第二份。知识库的字面那一路就是它 |
| `Embedder#id()` 的契约（MC 侧） | **照抄**。向量与 embedder 必须绑定 |
| `VectorIndex.blend` 的 clamp 教训 | **照抄**。cosine 不 rescale |
| `IndexCache`（2026-10-30 加） | 知识库**也需要**同样形状的缓存；但失效依据不同（见下） |
| 降级风格（Hub 挂了 MC 照常） | 一致：嵌入挂了检索照常 |

**关于 `IndexCache` 的复用**：知识库的索引缓存**不能**直接复用记忆那套。
记忆的失效依据是"三张表的行数指纹"，而知识库的失效依据是
**`kb_chunk` 的 `embed_state='done'` 计数** —— 因为一条 chunk 从 pending
变成 done 时，**行数不变但可检索集合变了**。这是同一个坑的第二次出现，
必须在代码里写清楚。

### 12.2 实施中被实测推翻的又一处设计

**§4.2「整篇够短就不切」这条规则是错的。**

第一版按 §4 写的：`chars(content) <= limit` 就不切。实测一份 200 字的文档，
里面写了 `# 材料` / `# 建造` / `# 食物` 三节，整篇被塞成**一块**。
后果直接可见：

| 查询 | 整篇一块 | 按标题切三块 |
| --- | --- | --- |
| 我该吃什么 | vec=0.339，且拿到的是混合内容 | vec=0.335，**精确命中「食物」段** |
| 屋子墙用什么建 | vec=0.370 | **vec=0.610**，命中「建造」段 |

修正后的规则：**有标题就按标题切，哪怕整篇很短**。
「短就不切」只适用于**没有结构**的纯文本 —— 有标题就说明作者已经给出了
语义边界，不用白不用。

这条是实施时跑真机发现的，设计阶段只看语料长度分布看不出来。

### 12.3 真机联调结果

环境：Ollama `192.168.3.252:11434`，`qwen3-embedding:0.6b-q8`，512 维。

导入一份 5 小节的生存手册（规则/材料/建造/食物/安全），5 块，嵌入 5/5 成功。

| 查询 | 命中 | vec | lit |

| 我的房子墙应该用什么 | 建造要点 ✅ | 0.516 | **0.000** |
| 什么东西会突然爆开 | 安全和危险 ✅ | 0.502 | **0.000** |
| 饿了该吃什么 | 食物与生存 ✅ | 0.457 | 0.977 |
| 半夜能不能一个人下矿 | 安全和危险 ✅ | 0.572 | **0.000** |
| 会被封号吗 | 服务器规则 ✅ | 0.553 | **0.000** |
| 地基建多深才稳 | 建造要点 ✅ | 0.544 | 1.000 |

**7/7 命中正确小节，其中 4 条 `lit=0.000`** —— 字面完全没有重叠，纯靠向量。
这是「加嵌入」这件事价值的直接证据。

### 12.4 实施中发现并处理的两个坑

**① 注释里的转义被写成了真实字符。** 写 `content_hash` 时，注释里写
`\r\n` 被当成真实回车写进了源码，把一行注释劈成两半导致编译失败。
教训：**注释里的转义序列要么别写，要么写清是全角/描述性的**。

**② `Config` 的 `derive` 被新类型抢走了。** 插入 `KbConfig` 时把原本属于
`Config` 的 `#[derive(Debug, Clone, Serialize, Deserialize)]` 接到了
`KbConfig` 头上，`Config` 反而丢了 derive。报错是
「conflicting implementations of trait `Clone` for type `KbConfig`」——
看着像重复定义，实际是**注释块和 derive 被切开了**。
教训：用脚本插入结构体时，anchor 要包含注释块**和** derive，不能只匹配 `pub struct X {`。

### 12.5 还没做的

1. **面板的知识库页** —— 现在只能用接口，不能点
2. **文件/URL 导入** —— 只有「贴文本」
3. **8b-q8 的公平对比** —— 当前 0.6b 是 Q8、4b/8b 是 Q4，混了量化变量
4. **/v1/context 的知识库段** —— 按 §9 阶段 6 的建议刻意没做

### 13.1 部署结果

部署前用线上库副本演练过迁移：8→9，618/165/22 条数据一条不差。

### 13.2 部署时抓到的两个真 bug

**① `no_proxy()` 缺失 —— 表现为「终端能跑、开机自启不能跑」**

同一个二进制、同一份配置：终端手动启动能连上 Ollama，由 **launchd** 启动却报
`error sending request`。两边环境变量里都没有 proxy 相关设置。

根因是 reqwest 默认会读系统代理配置（macOS 上走 `system-configuration`），
而 launchd 环境的读取结果与终端不同。修复：客户端构造时显式 `.no_proxy()`。

> 这个 bug 之所以难查，是因为**错误信息被吞了**。修复过程中顺手把
> reqwest 的 `Error::source()` 链也拼进错误文本里 —— 之前只显示
> 「error sending request」，真正的原因（连接被拒 / DNS / 超时）
> 在 source 链里看不到。没有那条链，只能靠猜。
>
> 判据：`客户端显式禁用代理`、`连接失败的错误信息带底层原因`。

**② 嵌入计数没排除已删文档**

面板显示「已嵌入 10 块」，而实际只有 5 块可用 —— 因为被删文档的块
还留在表里（逻辑删除），被一起统计了。运维会以为删除没生效、或者自己导了两份。

修复：`embed_counts` 加 `JOIN kb_doc ... WHERE d.deleted_by IS NULL`。
判据：`嵌入计数不含已删文档`。

### 13.3 检索路径加了冷加载重试

`Embedder::embed` 失败后重试一次（间隔 300ms）。

**为什么检索要重试而回填不重试**：检索路径上的失败大多是「模型正在冷加载」。
Ollama 空闲几分钟就卸模型（`keep_alive` 默认 5 分钟），下一个查询要 ~600ms 重载；
若撞上连接超时，那一次检索就丢掉了语义召回。实测「封号」查「封禁」**纯靠向量，
字面一条都不中** —— 向量失败就等于零结果。

回填任务不重试是对的：那里有退避机制，且批量失败说明服务真的挂了。

真机验证：手动卸载模型后首次查询，1.18 秒返回，`degraded=null`，正常命中。

### 13.4 面板功能

侧栏新增「知识库」页（`/api/admin/kb*`，**会话鉴权**，与 `/v1/kb/*` 的 token 鉴权互不替代）：

| 功能 | 说明 |
| --- | --- |
| 库列表 | 每库的文档数、块数、已嵌入/待嵌/失败 |
| 新建库 | id + 名称 + 说明 |
| 导入文档 | 选库、标题、来源、粘贴内容（支持 markdown 标题分块） |
| 文档列表与删除 | 抽屉里列出该库所有文档，可逐篇逻辑删除 |
| 检索测试 | 直接验证效果，标出每条是**靠向量**还是**靠字面**命中 |
| 块详情 | 点结果看正文、嵌入状态、重试次数、错误原因 |
| 重建向量 | 全库或按库重置为 pending（换模型/维度后必须做） |

**检索测试里那个 `lit=0.000` 标记是有意做的**：它让「这条是纯语义命中」
一眼可见，而不是让人去猜为什么字面完全不像却排在前面。

**面板比 API 多的是运维视角**：每个块嵌入了没有、失败原因是什么、
积压多少。只说「检索不准」而不说「有 3 块嵌失败、错误是超时」，
等于没说。

## 14. 文档查看与编辑（2026-10-30 补）

### 14.1 第一版漏了什么

第一版面世时，文档只能**导入**和**删除** —— 看不了内容、改不了字。
用户第一眼就指出来了：「这个手册不能查看和修改吗？」

这不是「少个按钮」，是**数据模型缺一列**：

```sql
-- schema 9 的 kb_doc
id, kb_id, title, source, content_hash, n_chunks, created_ms, updated_ms, deleted_by
--                                                            ↑ 没有 content
```

原文没存，只存了切出来的块。后果是三件事都做不了：

1. **看不了原样** —— 只能看到切碎的块，拼不回原文的相对格式
2. **改不了** —— 改了不知道以什么为准（块改了会和原文不一致）
3. **换分块参数重切不了** —— 原文已经不存在了

### 14.2 补的是什么

**schema 9 → 10**：`kb_doc` 加 `content TEXT`（列级 `add_column_if_missing`，老库自动补）。

**真相是原文，块是派生物。** 这条决定了编辑的方向：

| 操作 | 行为 |
| --- | --- |
| 改标题 | 不动块（`rechunked=false`） |
| 改内容且内容真变了 | 旧块**物理删除** → 重新切块 → 新块置 `pending` → 催一次回填 |
| 改内容但内容没变 | 只更新标题，**不白重切**（重切会让所有块重新嵌入，几十秒的活） |
| 改成与同库另一篇一样 | 报可读的错误（而不是撞唯一索引给一句 SQL 报错） |
| 内容改空 | 拒绝 |

**为什么不支持逐块编辑**：块是派生物。允许逐块改会导致原文与块不一致，
而之后任何一次重新切块都会把逐块修改悄悄抹掉 —— 那种「改了但过几天没了」
是最难排查的一类问题。所以只做**文档级**编辑，链路单向。

**老文档（schema 9 导入的）怎么办**：`content` 为 NULL 时，`kb::reassemble`
从块拼回 `# 标题\n正文` 的格式，并在响应里标 `content_reassembled: true`。
面板据此提示「这份是重建的，保存会把拼回来的内容当作新原文」。

### 14.3 端到端验证

改前 5 块（5 个小节）→ 改内容新增「常用坐标」一节 → 重新切成 **6 块**
→ 自动嵌入 `done=6` → 查询「我家在哪」命中「常用坐标」，
**`vec=0.466 / lit=0.000`** —— 字面完全没重叠（「我家」vs「家的位置」），纯靠语义。

判据：`能取回文档原文与块明细`、`老库没存原文时从块拼回来`、
`改标题不动块`、`改原文会重新切块并置为待嵌入`、
`改成与另一篇相同会被拒绝`、`内容没变时不白重切`、`空内容不能保存`。

## 15. 面板交互修复（2026-10-30 第二轮）

用户截图指出：「标注的两个都无法点开，或是点击没反应」。
查下来是**三个叠加的 bug**，一个比一个隐蔽。

### 15.1 bug 1：`api()` 只发 GET，写操作静默失效

```js
// 修复前
async function api(path){        // ← 只有一个参数
  const r = await fetch(path, {headers:{'Accept':'application/json'}});
  ...
}

// 我写成了
await api('/api/admin/kb', {method:'POST', body:...});
//       ↑ 第二个参数被完全忽略，实际发的是 GET
```

后果：**新建库、导入、删除、重建向量、保存编辑全部是空转**。
面板上表现就是「点了没反应」，而服务端日志里连请求都没出现（因为发的是 GET）。

修复：`api(path)` 保留（纯 GET），新增 `apiDo(method, path, body)`。
**刻意不给 `api` 加重载**——那个疏忽正是「传了参数却被忽略」造成的，
独立的函数名让「要写」这件事在调用点可见。

### 15.2 bug 2：事件绑定选错了 DOM 作用域

```js
// 修复前
c.querySelectorAll('[data-doc]').forEach(...)   // c = 主内容区
```

但 `showDrawer()` 把 HTML 写进的是 `$('drawerBody')`，**不在 `c` 里面**。
所以 `querySelectorAll` 永远返回空集合，一次绑定都没发生。

修复：抽屉里的事件一律绑到 `dbody = $('drawerBody')`。

> 这类错误的特征是「查不到元素但也不报错」——`forEach` 空集合是完全合法的。
> 现在知识库页里只有三处 `querySelectorAll`，两处用 `dbody`、一处用 `c`，
> 各有明确理由。

### 15.3 bug 3：`rechunked` 报告的是「客户端传了什么」而非「实际做了什么」

`update_doc` 内部：内容哈希没变就跳过重切（只改标题时不值得重跑几十秒的嵌入）。
但接口层把 `rechunked` 算成 `b.content.is_some()` —— 客户端总是会传 content
（面板把文本框内容整个发过来），于是哪怕什么都没重切，也返回 `rechunked: true`。

用户会看到「已重新切块，向量正在重新生成」然后等一个不会发生的过程。

修复：`update_doc` 返回 `(块数, 是否真的重切了)`，接口层如实透出。

> **这个 bug 是被 Node 模拟脚本抓到的**，不是靠看代码。脚本按顺序跑
> 「读→建→导→看→改标题→改内容→删」，在「改标题」那一步断言
> `rechunked === false` 才暴露出来。

### 15.4 顺手改的交互

「查看 / 编辑」从「点整行」改成**显式按钮**，与「删除」并列（删除是红色）。
用户的建议是对的：可点区域不该靠猜，两个动作长得一样、位置一样最不容易错。

### 15.5 判据

- `改标题不动块` + 断言 `rechunked == false`
- `改原文会重新切块并置为待嵌入` + 断言 `rechunked == true`
- 面板侧用一个 Node 脚本走完 9 个交互（含 5 个写操作），
  断言每一步的**实际效果**而不只是 HTTP 200

### 15.6 教训

**「按钮点了没反应」通常不是按钮的问题，是请求根本没到后端。**
这次三个 bug 里有两个（api 只发 GET、作用域选错）都会让请求完全不到服务端，
而服务端这边一切正常、日志干净 —— 从后端排查会一无所获。

写前端交互时，**用脚本把「用户点一下会发生什么」完整跑一遍**，
比在浏览器里手点更可靠：手点只会发现「没反应」，脚本能告诉你卡在哪一步。

## 16. 接入 `/v1/context`（2026-10-30 第三轮）

### 16.1 用户看到的现象

NPC 在 QQ 里被问「服务器的生存手册是什么」，回答：

> 服务器那本"生存手册"我还真没存过。……我这边只记得自己干过的事，
> 不记得别人写下来的规矩。

这是**准确的**。查证结果：

| 检查 | 结果 |
| --- | --- |
| MC 插件调用 `/v1/kb/*` | **0 处** |
| AstrBot 插件调用 `/v1/kb/*` | **0 处** |
| `/v1/kb/search` 接口本身 | 正常，能命中 |

**知识库建好了，但没有任何客户端查它。** 按 §9 阶段 6 的建议，
第一版刻意没把它并进 `/v1/context` —— 但那就意味着它只能被显式调用，
而改两个插件（Java + Python）的成本被我低估了。

### 16.2 改了主意，理由

原设计说「插件在需要时主动调 `/v1/kb/search`」。实际问题是：

- MC 插件（Java）自己拼 prompt，**不走** `/v1/context`
- AstrBot（Python）走 `/v1/context`

两条完全不同的集成路径，要改两处、两种语言、两次测试。

而 `/v1/context` 是现成的、两个客户端里至少一个已经在用的入口。
**加一段 = 一处改动**，QQ 立刻就能用上。

原设计反对合并的理由是「外部资料不属于『我是谁』，模型会分不清」。
这个担心是成立的，但它有解：**给这一段一个明确到不可能误解的标题**——

```
# 你查到的资料（不是你的亲身经历）
- 【服务器规则】禁止使用作弊模组……
```

不是靠模型自觉，是靠文案把「亲历」和「查到」在措辞上分开。

### 16.3 注入门槛是实测出来的

**不做门槛的话，每轮闲聊都会塞一段不相关的东西**，挤掉真正有用的段。
实测（6 块语料，真实数据）：

| 类型 | 查询 | top1 vec | top1 lit |
| --- | --- | --- | --- |
| 相关 | 服务器的生存手册是什么 | 0.408 | 0.676 |
| 相关 | 怎么弄到做鱼竿的材料 | 0.592 | 1.000 |
| 相关 | 会被封号吗 | 0.554 | 0.000 |
| 相关 | 我家在哪 | 0.466 | 0.000 |
| **无关** | 今天天气不错 | **0.351** | 0 |
| **无关** | 你好呀 | **0.359** | 0 |
| **无关** | 1+1等于几 | **0.309** | 0 |
| **无关** | 随便聊聊 | **0.297** | 0 |
| **无关** | 鲸鲸你真可爱 | **0.286** | 0 |

**无关查询也能拿到 0.29~0.36** —— 区分度比预想的薄得多。
0.42 这条线是**卡在最接近的噪声（0.359）和最低的相关（0.408）之间**，
不是拍的。

门槛可配（`BLUEWHALE_KB_INJECT_MIN_VEC` / `_LIT`），**语料变大后要重测**：
小语料上「什么都有一点相似」，语料一大，无关项的相似度会整体下降。

### 16.4 段落位置

`plan → memory → kb → events → group → diary → mood`

放在 `memory` 之后、`events` 之前：问事实性问题时资料比「最近发生的事」更直接。
没有命中时 `render_kb` 返回 `None`，**这一段根本不出现**，不占预算。

| --- | --- |

判据：`context_在命中时注入知识库段且位置正确`、`context_无关提问不注入知识库`、
`context_知识库关闭时不出现_kb_段`。

### 16.6 仍然没做的

**MC 插件（游戏内 NPC）还拿不到知识库。** 它不走 `/v1/context`，
而是用 `CompanionPrompt` 在本地拼 prompt。要让它也用上，需要：
1. `HubClient` 加一个 `/v1/kb/search` 的调用
2. `CompanionPrompt` 里加一段，位置在「你记得的事」之后

这是 Java 侧的独立改动，测试基础设施在 `插件/AiNpc/tools/`。

## 17. MC 插件（Java 侧）接入（2026-10-30 第四轮）

### 17.1 为什么它需要单独改

`/v1/context` 那条路只覆盖 QQ（AstrBot 走它）。**游戏内的 MC 插件不走 `/v1/context`** ——
它用 `CompanionPrompt` 在本地拼提示词，数据靠 `RemoteMemoryRepository` 一条条取。
所以要让它也用上知识库，只能改 Java。

### 17.2 改了什么

**新增 `插件/AiNpc/src/main/java/com/mc/deepseekmc/companion/KbSearch.java`**

- 调 `POST /v1/kb/search`（`HubClient` 已有 `post` 方法，没加新依赖）
- **门槛判定与预算裁剪抽成纯函数** `passesGate` / `fitsBudget`，以便离线可测
- 任何失败（中枢不可达 / 401 / 超时 / JSON 变了）→ 返回空列表，**绝不抛异常**

**`CompanionPrompt` 加一段**，位置在「你记得的事」之后、群聊之前：

```java
// ---- knowledge base: external reference material, NOT personal memory ----
int kbLeft = budget - used;
if (kbLeft > 60) { ... KbSearch.forPrompt(query, kbLeft) ... }
```

### 17.3 三个必须做对的地方

**① 阈值必须和中枢侧一致。** Java 里写死 `MIN_VEC=0.42 / MIN_LIT=0.30`，
注释里标明「与中枢 `kb.inject_min_vec` 同值，两边一起改」。
判据里有一条**断言这两个数字**，防止有人单边改动造成两边行为分裂。

**② 失败即空，不抛异常。** 知识库是增强，不能因为它挂掉让整轮对话失败。
真机验证：中枢不可达（端口 9）与 token 错误（401）都返回 0 条、无异常。

**③ 装不下就跳过，不截断。** 截断的资料是半句话，比没有更糟 ——
它会引导模型往错的方向接下去。

### 17.4 离线判据 `tools/kbcheck/`

30 条断言，不联网、不起服务、不碰 Forge：

| 组 | 覆盖 |
| --- | --- |
| 门槛 | 用真机实测的 8 个分数（4 相关 / 4 无关）验证分界线；「或」关系；`>=` 边界 |
| 常量 | 断言 `MIN_VEC==0.42`、`MIN_LIT==0.30` 与中枢一致 |
| 预算 | 充足时最多 2 条；极小预算给 0 条；只够一条给完整的一条；长条装不下时仍给短条 |
| 渲染 | 标题含「不是你的亲身经历」；换行压单行；无小节名不输出空方括号 |

`tools/run-all.sh` 会自动发现 `tools/*/run.sh`，所以 kbcheck **自动纳入了统一检查**
（45 套，全过）。

> 写判据时自己踩了一个坑：一开始把「长条装不下」的预算设为 260，
> 但 200 字的长条在 260 预算下其实装得下 —— 断言失败后才发现是**测试参数算错**，
> 不是代码错。改成 150 才真正构造出那个场景。

### 17.6 还没做的

- **没有在真实服务器里跑过对话**。判据与联调覆盖了「能不能拿到资料」和
  「该不该注入」，但「模型看到这段之后答得对不对」只能在游戏里验证。
