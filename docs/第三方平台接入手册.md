# 对接手册：给第三方平台接入蓝鲸记忆中枢

> 面向**任何想接这套记忆的平台**：Minecraft 插件、QQ / 微信机器人、直播弹幕、
> 语音助手、桌面或手机客户端。
>
> 全部示例都是在本机生产实例上真实跑出来的响应（2026-11-01），不是设计稿。
> 只写「照着做就能通」的部分；为什么这么设计，见 [`架构方案.md`](架构方案.md)。

---

## 0. 先理解它在做什么

它是一个**单主体**记忆服务：**只服务一个对象**（下称「它」）。

```
        ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
        │  MC 插件     │   │ QQ 机器人    │   │ 直播弹幕     │  ← 你的平台
        └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
               │  写记忆（事件/事实/消息）  │  读上下文  │
               └───────────────┬─┴────────────────┘
                               ▼
                    ┌────────────────────┐
                    │   蓝鲸记忆中枢      │  一个二进制 + 一个 .db
                    │  /v1/*  (API token) │
                    └────────────────────┘
```

**你只需要做两件事**：

1. **写**：把平台上发生的事告诉它（`POST /v1/event`、`/v1/message`）；
2. **读**：回答前把它该记得的事取回来，拼进 system prompt（`GET /v1/context`）。

除此之外**没有必需的依赖**：不接也能跑，接错了最多是「它记不住」，不会把你的业务流程弄挂。

## 1. 三十秒上手

```bash
HOST=http://<中枢地址>:25590
TOK=<BLUEWHALE_TOKEN>

# 1) 探活（不需要 token）
curl $HOST/v1/health

# 2) 写一条记忆
curl -X POST $HOST/v1/event \
  -H "X-API-Token: $TOK" -H "Content-Type: application/json" \
  -d '{"channel":"mc","kind":"task.done",
       "summary":"盖好了小屋的东墙","importance":0.85,
       "dedup_key":"mc-2026-11-01-wall-east"}'

# 3) 回答前取上下文（一整段可直接拼进 system prompt）
curl -G $HOST/v1/context -H "X-API-Token: $TOK" \
  --data-urlencode "q=你最近在忙什么" --data-urlencode "scene=group"
```

三条就够跑通。下面是每条做对的细节。

## 2. 鉴权：两条链，互不替代

| 入口 | 凭据 | 给谁 |
| --- | --- | --- |
| `/v1/*` | **`X-API-Token` 请求头** | 你的程序（本手册全部内容） |
| `/`、`/api/admin/*` | **浏览器会话 cookie** | 人在网页上管理 |

- **token 只走请求头**，不要拼进 URL（URL 会进访问日志、反向代理日志）。
- 面板 cookie **不能**调 `/v1/*`；程序 token 也不该塞进浏览器。
- 失败返回 `401`，响应体是 `{"error":"未授权",...}`。
- `/v1/health` 免 token，且**只返回计数**，不返回任何记忆内容。

## 3. 三个必须理解的概念

### 3.1 单主体：不需要传「谁在记」

所有记忆天然属于它。**旧字段 `companion_id` 已经删除**：

- 继续传不会报错（多余字段被忽略），但**没有任何作用**；
- 别按它做分库、分表、分检索。

### 3.2 `channel`：在哪发生的（**可维护，不写死**）

`mc` / `qq` / `live` / `system` 是内置的四个，但渠道**不是编译期枚举**：
面板「渠道」页可以新增任意 tag（如 `bilibili`、`wechat`），加完就能直接用。

```bash
# 写之前先问一句有哪些（可选，但省事）
curl -H "X-API-Token: $TOK" http://<主机>:25590/v1/channel/list
```

| 内置 tag | 用于 | 默认可信度 |
| --- | --- | --- |
| `mc` | Minecraft 里的经历 | 1.0 |
| `qq` | QQ 群 / 私聊 | 0.9 |
| `live` | 直播间弹幕 | 0.8 |
| `system` | 你自己的后台任务 | 1.0 |
| 自定义 | 面板里新加的 | 0.8（可单独调） |

**没注册过的 tag 会当场 `400`**，并在错误里告诉你去哪看列表 ——
这样拼错的 `Qq ` / `qqq` 不会悄悄写进库、变成面板上一个谁也认不出的渠道名。

可信度决定这条记忆在检索里的先天权重（弹幕可能有玩笑和反串，所以低于 MC）。

### 3.3 `at_ms`：唯一时间主轴

所有时间是**现实 UTC 毫秒**。不填 = 现在。

> 游戏内时钟（`g<N>`）、直播场次编号都只是**标签**，不要拿它们排序或回滚。

## 4. 写：把发生的事告诉它

### 4.1 `POST /v1/event` —— 一件发生过的事

```json
{
  "channel": "mc",
  "kind": "task.done",
  "summary": "盖好了小屋的东墙",
  "importance": 0.85,
  "at_ms": 1793085937278,
  "dedup_key": "mc-2026-11-01-wall-east",
  "person_id": "p-gleam",
  "scope": "companion",
  "channel_day": "g1024"
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `channel` | ✅ | `mc` / `qq` / `live` / `system` |
| `kind` | ✅ | 你自己的类型串（`task.done`、`player.talked`…），自由取 |
| `summary` | ✅ | **一句话，会进提示词**。写清楚「发生了什么」，别写「操作成功」 |
| `importance` | | `[0,1]`。**不传 = 中枢自动判定**（推荐，见 §4.5）；传了就按你的值 |
| `at_ms` | | 不填 = 现在 |
| `dedup_key` | | **强烈建议填**，见 §4.3 |
| `person_id` | | 涉及的人（见 §6） |
| `scope` | | `player` / `companion` / `shared` / `world`，默认 `companion` |
| `channel_day` | | 仅 MC：游戏日标签，只存不排序 |

响应：

```json
{"id": 393, "duplicate": false}
```

`duplicate: true` 表示 `dedup_key` 已存在，这次被忽略（`id` 为 `null`）。

### 4.2 `POST /v1/message` —— 原话（聊天 / 弹幕）

```json
{
  "channel": "qq",
  "group_id": "123456",
  "account": "478889187",
  "sender_name": "啥子猫",
  "content": "姆姆又偷偷加强自己和鱼了",
  "at_ms": 1793462511924,
  "message_id": "7468392018"
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `channel` | ✅ | `qq` / `live` |
| `content` | ✅ | 原话，**不要润色** |
| `at_ms` | ✅ | 发生时刻 |
| `message_id` | | 平台消息 id。**天然幂等键**，强烈建议填 |
| `group_id` | | 群/房间号。**空 = 私聊**，中枢据此切场景（见 §5.3） |
| `account` | | 发送者账号（QQ 号 / uid）。用于跨渠道认人 |
| `sender_name` | | 当时的**显示名**（会随群名片变） |

响应：`{"ok": true, "inserted": true}`

> **`message_id` 别传空串**：中枢把空串当成一个**真的** id，
> 第一条写进去之后，同渠道所有空串 id 的后续消息都会被判重复而**静默丢弃**。

### 4.5 重要度：默认由中枢自动判定

**不传 `importance` 时**，中枢从四个维度算一个值，并把依据存进 `importance_reason`：

| 维度 | 作用 |
| --- | --- |
| 类型基底 | `died` 0.78 / `attacked` 0.72 / `promise` 0.62 / 对话 0.55 / 闲聊 0.30 |
| 关系 | 涉及的人与它越亲近，加得越多（最多 +0.20） |
| 命中 | 摘要命中了既有事实 → 最多 +0.15（说明这条在补充/推翻已知） |
| 自我 | 摘要提到它自己 → +0.10 |
| 噪声 | 纯标点、纯重复、常见应答词（「好的」「666」）→ −0.10（扣不死） |

为什么不让接入方拍常数：以前 QQ 群消息一律 0.3、被 @ 的一律 0.6，
于是「被苦力怕炸死」和「今天天气不错」在检索里权重一样，记忆一多就被闲聊淹掉。

**想做 AI 判断**：中枢不调模型（它是存储服务），但自动值只是默认值 ——
你可以在自己那一侧判完再 `PATCH /v1/event/{id}` 覆盖，`importance_source` 会变成 `manual`。

### 4.6 事件摘要里的昵称会被换成身份显示名

写事件时，中枢会**按这条事件自己的渠道**把摘要里的昵称替换成身份显示名：

```
{"channel":"qq","summary":"啥子猫在群里说：怎么还藏私明明还有"}
→ 入库后：          "姆姆在群里说：怎么还藏私明明还有"
```

为什么入库时就换：群名片会改（`啥子猫` → `啥子喵`），历史记录留着旧名字，
之后就再也关联不上；换成显示名后同一个人的所有事件天然能用**一个词**检索到。

**不做全渠道匹配**：`mc` 渠道的事件里出现 QQ 群名片是很可疑的，
顺手改掉会掩盖真正的数据问题 —— 所以只按该事件自己的渠道查映射。

### 4.3 `dedup_key` —— 为什么必须填

网络重试、进程重启补发、事件重放都会让同一条记忆写两次。
中枢靠 `dedup_key` 判重（唯一索引），**重放是安全操作**。

键要**稳定且唯一到这一次事件**：

```text
mc-<日期>-<事件特征>            mc-2026-11-01-wall-east
qq-<群号>-<message_id>          qq-123456-7468392018
live-<房间>-<弹幕 id>           live-88-39512746
```

不要用时间戳当键（重试时时间会变，判不了重）。

### 4.4 `POST /v1/fact` —— 它「相信」的一件事

跟事件不同，事实是**可以被新版本取代**的长期认知（「主人爱吃的：鱼」）。

```json
{
  "channel": "mc",
  "key": "主人爱吃的",
  "value": "烤鱼",
  "person_id": "p-gleam",
  "tier": "curated",
  "importance": 0.8
}
```

| 字段 | 说明 |
| --- | --- |
| `key` | 同一个 `(person_id, key)` 只会有一条有效版本，旧的标 `superseded_by` |
| `value` | 值 |
| `tier` | `curated`（人写的，**不衰减**）/ `extracted`（推断的，会衰减） |
| `confidence` | `[0,1]`，默认 0.5 |
| `expires_ms` | 可选过期时刻 |

响应：`{"id": "f-1793462511924-1234", "superseded_by": null}`

## 5. 读：回答前取回上下文

### 5.1 `GET /v1/context` —— 一次调用拿全（**推荐**）

```
GET /v1/context?q=<用户刚说的话>&scene=group&budget=1200&topk=5
```

| 参数 | 缺省 | 说明 |
| --- | --- | --- |
| `q` | `""` | 用户刚说的话。用它挑相关记忆；空 = 只按时间/权重取 |
| `scene` | `group` | `group` 或 `private`。**不传默认 group**（安全侧） |
| `budget` | `1200` | 返回文本的字符上限，clamp `[200, 4000]` |
| `model` | `""` | 这一轮用的模型 id。用它匹配「人格」正则（见 §5.4）；不传 = 只用兜底人格 |
| `topk` | `5` | 记忆条数上限，clamp `[1, 30]` |

响应（真实）：

```json
{
  "text": "# 你最近在做什么\n- 今天的打算：矿也挖了、煤也攒了…\n\n# 你记得的事\n- …",
  "chars": 581,
  "parts": ["plan", "memory", "names", "events", "group", "diary", "mood"],
  "dropped": ["diary: 超预算", "group: 超预算"],
  "generated_ms": 1793466421225,
  "scene": "group"
}
```

| 字段 | 说明 |
| --- | --- |
| `text` | **可直接拼进 system prompt 的 markdown**。没有可注入内容时是空串 `""`，不是 null |
| `chars` | `text` 的字符数（不是字节数） |
| `parts` | 实际进来了哪几段，排查「它为什么没提这件事」先看这个 |
| `dropped` | 被预算挤掉 / 读取失败的段落及**具体原因** |
| `scene` | 服务端**实际采用**的场景（排查「我传了 private 怎么还像群聊」） |

段顺序固定，预算不够时**从下往上丢**：

```
plan(它打算做什么) → memory(相关的记忆) → names(称呼对照)
  → kb(知识库) → events(最近发生的事) → group(群里最近说的话)
  → diary(上次的日记) → mood(此刻心情)
```

用法建议：

- **必须**把 `text` 原样拼进 system prompt，**不要**再二次截断或改写（预算逻辑在中枢）；
- 记 `chars` 做用量统计；`text == ""` 时不要拼空段；
- `dropped` 非空不必告警，那是正常的预算行为。

### 5.2 `GET /v1/recall` —— 只要记忆条目

```
GET /v1/recall?q=钻石&topk=5
```

返回数组（真实）：

```json
[{"kind":"event","id":"6","at_ms":1793086117278,
  "text":"在 y=-54 发现了钻石矿脉",
  "weight":0.813,"why":"关键词命中","hit":true,"score":1.0,
  "matched":["钻石","钻","石"]}]
```

| 字段 | 说明 |
| --- | --- |
| `weight` | 重要性 / 时效 / 渠道可信度决定的**固有**权重，与提问无关 |
| `score` | 与提问的相关度 `(0,1]`，**0 = 纯兜底**（没命中关键词） |
| `why` / `hit` / `matched` | 命中原因与命中的词，用于解释「它为什么想起这个」 |

检索是**中文 BM25**，不是子串匹配；同义词查不到（问「diamond」找不到「钻石」）。

### 5.3 `scene` —— 隐私边界，别乱传

- `group`：只给群聊里说过的话；
- `private`：只给私聊内容。

**裁剪发生在服务端**，你只要如实声明「这条消息来自群还是私聊」。
把私聊消息标成 `group`，等于把私聊内容播给全群——这是本系统里最容易犯的错。

---

### 5.4 人格：按模型 id 正则匹配（可选）

同一个角色在不同模型上往往要不同的叮嘱（小模型要更强的格式约束，
推理模型要更少的「慢慢想」提示）。所以人格是**一条条可匹配的卡片**：

- 面板「人格」页维护：名字、匹配的模型 id（**正则**）、优先级、正文；
- 调 `/v1/context?model=<模型id>` 时，命中的那条会以 `# 你是谁` 段
  拼在**上下文最前面**（`parts` 的第一个是 `persona`）；
- **正则为空 = 兜底，优先级永远最低**（不管 priority 填多少）——
  否则一条 priority=99 的兜底会盖住所有精确匹配；
- 写坏的正则会被当场拒绝（存进去等于这条永远不生效，最难查）。

不传 `model` 时只会命中兜底人格：调用方没报模型 id 时，
不该让一条 `deepseek.*` 的专用人格顶上。

## 6. 跨渠道认人（这是「跨渠道记忆」的前提）

### 6.1 为什么需要

MC 玩家是 UUID、QQ 是 QQ 号、直播是 uid —— **三套 id 天然不通**。
中枢用 `person_id` 把它们指向同一个人；记忆挂在 `person_id` 上，绑定后两边记忆自动合并。

### 6.2 `POST /v1/person/bind`

```json
{"channel":"qq","account":"478889187","person_id":"p-gleam","seen_name":"啥子猫"}
```

- 同一个 `(channel, account)` 再绑一次 = 改绑；
- 响应带 `previous_person`：这个账号**之前**绑的是谁，用于追溯。

### 6.3 `GET /v1/person/pending`

列出还没确认归属的账号。**绑定必须人工确认，不要自动猜**——
同名不代表同人，猜错会把两个人的记忆混成一个人，而且不可逆。

> 中枢侧的「各场景称呼」（MC 里叫什么、QQ 群叫什么、直播间叫什么）在面板
> 「身份」页维护；程序侧**不需要**处理，但 `person_scene` 会影响
> §7 的称呼归一和上下文里的「称呼对照」。

## 7. 两个名字相关接口（强烈建议接）

同一个人在不同地方叫法不同：身份显示名「姆姆」、QQ 群名片「啥子猫」、MC 名「GleamSlime」。
模型只看到平台给的那个名字，于是会说错人。

### 7.1 `POST /v1/name/normalize` —— 发送前把名字统一

```json
{"text":"啥子猫说得对","scene":"qq_group"}
→ {"ok":true,"text":"姆姆说得对",
   "replacements":[{"from":"啥子猫","to":"姆姆","count":1}]}
```

- `scene` 可省略（= 所有场景的称呼都换）；
- 规则：只换 **2 字以上**、称呼≠显示名、**有歧义不换**（同名指向两人）、长名字优先；
- **纯文本改写，不动库里任何数据**；不调它也能正常收发，只是名字不统一。

建议的调用点：**回复发送前**（有 TTS 的话，要在**语音合成之前**，否则念的还是旧名字）。

### 7.2 上下文里的「称呼对照」（自动）

`/v1/context` 只在这句话**提到某个人**时，多给一小段：

```
# 称呼对照
同一个人在不同地方叫法不同，别当成两个人：
- 姆姆：MC 里叫「GleamSlime」、QQ 私聊叫「=ᗜωᗜ=」、QQ 群叫「啥子猫」
```

不需要你传参；没提到任何人就一个字都不加（不占预算）。

## 7.5 忽视名单：这个人的话要不要理

被设为「忽视」的人：**不回复、也不写进记忆**。判断放服务端，因为
`person_id` ↔ QQ 号的绑定只有中枢知道，接入方手里只有一个账号字符串。

```bash
curl -H "X-API-Token: $TOK" \
  "http://<主机>:25590/v1/person/ignored?channel=qq&account=478889187"
# → {"ignored":true,"person_id":"p-gleam","display_name":"姆姆"}
```

返回三个字段能区分三种情况：

| 返回 | 含义 |
| --- | --- |
| `ignored: true` | 别回复、别写记忆 |
| `ignored: false, person_id: "p-…"` | 绑过账号，正常处理 |
| `ignored: false, person_id: null` | **还不认识**这个账号（不是忽视），照常回，只是不跨渠道合并 |

**接入方必须自己去问它** —— 光在中枢勾上「忽视」不会改变你的行为。
参考实现（AstrBot 插件 `on_group_sync` 开头）：

```python
if await self._is_ignored(event):     # GET /v1/person/ignored
    event.stop_event()                # AstrBot：不调 LLM、不产生回复
    return                            # 同步/图片/唤醒也一并跳过
```

位置很关键：要放在**决定是否调 LLM 之前**。放在「回复之后」只能事后丢弃，
模型该花的 token 已经花了。

开关在面板「身份」页。为什么不放关系里：关系是「我怎么看这个人」（数值），
忽视是「要不要处理这个人」（开关）—— 混在一起就表达不出
「陌生但不想理」和「亲近但拉黑」这两个真实状态。

> 写入侧也拦了：被忽视的人 `POST /v1/message` / `/v1/event` 会被静默丢弃
> （返回 `inserted: false, ignored: true`）。所以哪怕你只接了回复侧忘了写侧，
> 也不会有他的话混进记忆。

## 7.6 承诺：会自动认，也可以直接写

`/v1/event` 的摘要里如果是一句**承诺**，中枢会**自动**落一条 `promise`：

```
"我今晚帮你把那两个箱子整理了。"  →  open 承诺，"due": 今晚
```

识别规则刻意保守（宁可漏，不可错）：

- 必须同时有 第一人称（我/本鱼/咱）+ 将来时（会/明天/等下…）+ 承诺动作（帮/修/挖…）；
- 问句不算（「我帮你行吗？」）、否定不算（「我不会」）、不确定不算（「我可能」）；
- 时限能抽就抽（马上/等会儿/今晚/明天/后天），抽不出就留空，不瞎猜。

也可以直接写：

```bash
curl -X POST -H "X-API-Token: $TOK" -H 'Content-Type: application/json' \
  -d '{"id":"pr-1","description":"明天帮你修屋顶","status":"open",
       "created_ms":1793000000000,"updated_ms":1793000000000}' \
  http://<主机>:25590/v1/promise
```

删除走 `DELETE /v1/promise/{id}`（逻辑删除，可回滚）。
**记错一条承诺比没记更糟** —— 它会一直挂在上下文里，变成一个根本没答应过的义务。

## 7.7 语音库：传上来、打分、拿去训练

发出去的语音存下来，人工打分后筛出「念得好」的那批去做训练素材。

```bash
# 上传（multipart）
curl -X POST -H "X-API-Token: $TOK" \
  -F "file=@reply.wav" \
  -F "text=今天也要好好吃饭" \
  -F "voice=feiyu" -F "style=cute" \
  http://<主机>:25590/v1/voice

# 列表 / 只看打过分的
curl -H "X-API-Token: $TOK" "http://<主机>:25590/v1/voice?rated=1"

# 下载原始字节
curl -H "X-API-Token: $TOK" -o out.m4a http://<主机>:25590/v1/voice/<id>/file

# 打分（1–5）与备注
curl -X PATCH -H "X-API-Token: $TOK" -H 'Content-Type: application/json' \
  -d '{"rating":5,"note":"语气自然，但「鲸」字咬得重"}' \
  http://<主机>:25590/v1/voice/<id>
```

**统一存 m4a**（1 分钟约 0.5 MB，wav 要 10 MB）。转不了就**原样存并保留真实后缀** ——
宁可存个不能直接训练的格式，也不要因为环境没装 ffmpeg 就把语音丢了。
类型按**魔数**判断，不信 `filename`。

## 7.8 记忆画面：图片也是记忆

图片靠**关键词触发**进上下文，和事件同一套思路。

```bash
# 上传（multipart；也可以传 base64 字段代替 file，但**仍必须是 multipart**）
curl -X POST -H "X-API-Token: $TOK" \
  -F "file=@fishing.png" \
  -F "caption=在湖边钓上来的一条大鱼" \
  -F "keywords=钓鱼,湖,大鱼" \
  -F "sender=姆姆" -F "channel=mc" -F "person_ids=p-gleam" \
  http://<主机>:25590/v1/image

curl -H "X-API-Token: $TOK" "http://<主机>:25590/v1/image?q=钓鱼"
curl -H "X-API-Token: $TOK" -o out.png http://<主机>:25590/v1/image/<id>/file
curl -H "X-API-Token: $TOK" -o thumb.jpg http://<主机>:25590/v1/image/<id>/thumb
```

**两种用途（服务提供方各自接一个）：**

| 用途 | 用哪个 | 行为 |
| --- | --- | --- |
| 让它「记得那张图」并能看到 | `/v1/context` | 命中关键词时**把图以 base64 内联**进上下文（多模态模型真能看到） |
| 想发一张图/表情包出去 | `GET /v1/image/pick?q=…` | 返回一张匹配的图 id，再取 `/file` 发出去 |

``/v1/context` 的细节（2026-11-01 口径）：

- 拿**最近 3 条消息**（不只是当前这句）去匹配 —— 群里常是
  「图 → 哈哈这啥 → 你说呢」的接力，只看当前句会漏掉图；
- 匹配到只给**图片 id**（`（图 id: img-xxx）`），**不内联 base64**；
- 命中会让 `recall_count += 1`。

> ⚠️ **重要：base64 塞进文本是错的。**
> 多模态模型看图走的是消息 `content` 数组里的
> `{"type":"image_url","image_url":{"url":…}}`（OpenAI 格式），
> **不是**文本里的 `![x](data:…)`。后者模型只会当一段乱码字符串读。
> 所以「附图片」必须由接入方做：拿到 id → 取 `/v1/image/{id}/file` →
> 放进自己请求的图片字段。第一版我写成了内联，2026-11-01 实测确认是错的。

参考实现（AstrBot）：

```python
# 从上下文里解析出 id
ids = re.findall(r"图 id: (img-[A-Za-z0-9_-]+)", 画面段)
for i in ids[:max]:
    data = GET f"{HUB}/v1/image/{i}/file"      # 带 X-API-Token
    req.image_urls.append(
        f"data:{ctype};base64,{base64.b64encode(data).decode()}"
    )
```

为什么插件要自己取图再转 data URL：`image_urls` 里的地址是**模型服务端**去拉，
而中枢在内网、还要 token，模型那边根本取不到。
- **`caption` 不参与匹配**：它只用来「让人和模型知道这张图是什么」（内联时作为图片描述）。
  早期版本拿 caption 做过 2 字滑窗匹配，实测误命中率极高 ——
  caption「今天我们一起去湖边钓鱼」会被「今天天气不错」「我们走吧」
  「一起吃饭吗」全部命中（共享 今天/我们/一起 这种没信息量的片段），
  结果几乎每句闲聊都把图塞进上下文；
- **关键词要 ≥2 字**：`鱼`、`湖` 这种单字太容易误伤，不算命中。
  想让它能被某句话触发，就把那句话里的**词**加进 `keywords`（`钓鱼,湖边`）；
- **不给 URL**：模型看不到图，给链接它只会瞎编「我看到了」。
  给的是「你记得有这么一张图，内容是什么」；
- 存原图 + 缩略图（列表页拉几十张原图会几 MB 起步）；
- **入库时 `caption` / `keywords` 至少填一个**（都不填的话它命中不了任何句子，只是占地方）；
- **按内容 sha256 去重**：同一张图重复上传返回 `duplicate: true` 和已有 id，不重复占盘。

**挑图：两种意图，排序相反**（`mode` 参数）：

```bash
# ① 发张表情包活跃气氛（默认）
curl -H "X-API-Token: $TOK" "http://<主机>:25590/v1/image/pick?q=开心,笑"

# ② 「你记得那次…吗」把具体那张翻出来
curl -H "X-API-Token: $TOK" "http://<主机>:25590/v1/image/pick?q=开心&mode=recall"
# → {"ok":true,"found":true,"mode":"recall","id":"img-…","file":"/v1/image/img-…/file"}
```

| `mode` | 用途 | 排序 |
| --- | --- | --- |
| `emoji`（默认） | 发张表情包 | **发得少的优先** —— 同一张不会反复刷屏 |
| `recall` | 想回忆起那张图 | **用得多的优先** —— 常说起的才是那张有代表性的；同次数时**最近用过的**在前 |

**为什么不合成一个默认**：这两个需求的排序是**反的**。
只做一种的话总有一边是错的（表情包会反复发同一张，或者回忆翻出一张从没用过的）。

- `q` 里每个词都要 ≥2 字；
- `mode` 拼错会**当场 400**（静默当 emoji 会让「想回忆」退化成「轮换」，
  结果看起来像随机发的）；
- 拿 `file` 那个路径取字节就能发出去。

### 7.8.1 两个「照着传说写就会踩」的坑（2026-11-01 实测）

**① `base64` 只能走 multipart，不能塞 JSON 体。**

`/v1/image` 与 `/v1/voice` 共用同一个 multipart 提取器，传
`Content-Type: application/json` 一律得到：

```
Bad Request：Invalid `boundary` for `multipart/form-data` request
```

想用 base64 也得用表单字段（`-F "base64=..."`），不是 JSON。

**② base64 必须是裸串**：带 `data:image/png;base64,` 前缀会被拒
（`base64 里有非法字符`）。而 QQ / 微信这类渠道拿到的恰好就是 data URL 形式，
接入方要自己剥掉前缀。裸串里的换行也要清掉，同样是非法字符。

**③ 用 aiohttp 的 `FormData` 时记得 `default_to_multipart=True`。**
它默认只在**出现文件字段**时才切 multipart；全字符串字段（正是 base64 的用法）
会被编成 `application/x-www-form-urlencoded`，然后撞上上面第 ① 条的 400。
文件形式不受影响，所以这个坑只在换用 base64 时才现形。

## 10. 三种典型接法

### 10.1 Minecraft 插件（Java，已上线参考实现）

```java
// 写：异步、超时 ≤500ms、失败只记日志（记忆不能卡 tick）
http.sendAsync(
    HttpRequest.newBuilder(URI.create(BASE + "/v1/event"))
        .header("X-API-Token", TOKEN)
        .header("Content-Type", "application/json")
        .timeout(Duration.ofMillis(500))
        .POST(BodyPublishers.ofString(body)).build(),
    BodyHandlers.discarding()
).exceptionally(e -> { log.warn("记忆写入失败：{}", e.toString()); return null; });
```

参考实现：`插件/AiNpc/src/main/java/com/mc/deepseekmc/companion/`
（`HubClient` 负责 HTTP，`RemoteMemoryRepository` 负责读写分流）。

### 10.2 QQ / 微信机器人（Python，AstrBot 示例）

```python
# 回答前：一次拿全上下文
params = {"q": user_text[:120], "scene": "group" if is_group else "private",
          "budget": 1200, "topk": 5}
ctx = await session.get(f"{BASE}/v1/context", params=params,
                        headers={"X-API-Token": TOKEN},
                        timeout=aiohttp.ClientTimeout(total=2))
block = (await ctx.json()).get("text", "")
if block:
    system_prompt += "\n\n" + block        # 原样拼，别再截断

# 回复发送前（TTS 之前）：把名字统一
fixed = await session.post(f"{BASE}/v1/name/normalize",
                           json={"text": reply},
                           headers={"X-API-Token": TOKEN})
reply = (await fixed.json())["text"]

# 每条消息入库（只进不出，不要用它发言）
await session.post(f"{BASE}/v1/message", json={
    "channel": "qq", "group_id": group_id, "account": sender_id,
    "sender_name": sender_name, "content": text,
    "at_ms": int(time.time() * 1000), "message_id": msg_id,
}, headers={"X-API-Token": TOKEN})
```

参考实现：`插件/astrbot_plugin_deepseek/main.py`。

### 10.3 直播弹幕（伪代码）

```text
每收到一条弹幕：
  POST /v1/message  {channel:"live", group_id:<房间>, account:<uid>,
                     sender_name:<昵称>, content:<弹幕>, message_id:<弹幕id>}
  # 只有被叫到（@ / 关键词）才回：
  GET /v1/context?q=<弹幕>&scene=group
  拼进 system prompt → 生成 → POST /v1/name/normalize → 发送
```

弹幕量大时**不要每条都写**：给 `importance` 低一点（0.2–0.3），或只写「被点名」的那些。

## 11. 八条铁律

1. **别阻塞主线程**：写记忆必须异步、超时短（≤500ms），失败只记日志。
2. **`dedup_key` / `message_id` 必须稳定**，同一件事重试要用同一个键。
3. **空串 id 归一成 NULL**：空串会被当成真的 id，永久吞掉后续同字段写入。
4. **`summary` 会进提示词**：写「发生了什么」，别写「操作成功」。
5. **`scene` 如实声明**：私聊内容标成 group = 播给全群。
6. **回答前取上下文要短超时**（≤2s）：它串在回答链路上，卡住等于用户干等。
7. **`/v1/context` 的 `text` 原样用**，不要再切分或截断（两套预算只会打架）。
8. **备份用 `/v1/snapshot`**，不要拷 `.db` 文件。

## 11.1 响应形态不统一（**实测容易踩**）

不同接口的「列表」返回形态**不一致**，接的时候别假设：

| 接口 | 返回 |
| --- | --- |
| `/v1/recall` | **数组** |
| `/v1/event/list`、`/v1/journal/list`、`/v1/diary/list`、`/v1/message/list` | **数组** |
| `/v1/person/pending`、`/v1/relation/list`、`/v1/trait/list`、`/v1/affect/list`、`/v1/promise/list`、`/v1/plan/list`、`/v1/snapshot/list`、`/v1/rollback/history` | **数组** |
| `/v1/self/get` | **单个对象或 `null`** |
| `/v1/mood` | **单个对象** |
| 面板用的 `/api/admin/*` | `{"items":[…],"total":…,"page":…}` |

所以拿 `/v1/*` 时基本可以当数组 / 对象处理；只有管理面板那套是分页包装。

## 12. 排错速查

| 现象 | 先查 |
| --- | --- |
| `401` | `X-API-Token` 是否带上、是否拼进了 URL（不行，必须走头） |
| `400 未知渠道` | `channel` 只能是 `mc` / `qq` / `live` / `system` |
| 写成功但读不到 | `dedup_key` 是不是被复用了；查 `GET /v1/event/list` |
| `duplicate: true` 但确实是新事 | 键里用了时间戳/随机串，换成稳定特征 |
| 上下文里没有某段 | 看 `dropped` 有没有写原因；再看 `parts` |
| 它总说「我不记得」 | `q` 是不是空着；`topk` 太小；`budget` 太小 |
| 记忆串了渠道 | `scene` 传错，或 `group_id` 该空没空 |
| 回复里名字不对 | 接 `/v1/name/normalize`（TTS 要在合成**之前**调） |
| 想确认「这一轮它到底看到了什么」 | 面板「运维 → 注入回放」，程序可 `POST /v1/injection-replay` 上报（body 是 `{"entries":[…]}`） |
| `503 存储不可用` 但其它接口正常 | 大概率是某个接口的 SQL 列/占位符对不上；把响应体里的 `error` 原文带上找维护者 |

数据层的排查（直接查库、为什么检索没返回、情绪为什么是这个值）见
[`查询手册.md`](查询手册.md)；`/v1/context` 的逐段格式见
[`对接契约-v1-context.md`](对接契约-v1-context.md)，示例代码见 [`对接指南.md`](对接指南.md)。

| POST | `/v1/prune` | 配额清理 |
| GET/POST | `/v1/kb*` | 知识库 |

错误统一格式：

```json
{"error":"请求不合法：importance 必须在 [0,1]","retryable":false,"kind":"bad_request"}
```

`kind` ∈ `bad_request` / `unauthorized` / `not_found` / `rollback` / `storage` / `config`；
`retryable: true` 只出现在存储类错误上。
